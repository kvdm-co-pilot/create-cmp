# ADR-0017: The receipt is attested by a party that is not its producer — CI, keylessly

- **Status:** proposed — awaiting Karel's signature (FIX-PLAN 2026-09-28, slice 8)
- **Date:** 2026-09-29

## Context

A stamped app's receipt (`qa/evidence/latest.json`) is written by the lane on the author's
machine and committed by the author. ADR-0005 binds it to the tree by `inputs.hash`, which makes a
receipt **stale-evident**: a receipt from another tree fails the recompute. It does not make it
**forge-evident**. The hash deliberately excludes `qa/evidence/` (`packages/receipts/src/inputs-hash.mjs`),
so a receipt edited consistently — verdict and the failing step flipped to PASS, durations kept
plausible — passes every check that reads it. The pattern review of 2026-09-28 showed this with an
instrument (finding D-1, `docs/research/PATTERN-REVIEW-2026-09-28/D-context-receipt-strategy.md`):
`evaluateReceipt`, `checkDoneEvidence`, `checkExecutionPlausibility` and `checkLaneVouching` all
said yes. `receipt-validate.mjs` already concedes that the verdict "is the most editable field on a
file the hash cannot cover".

The cause is one sentence: **the receipt's producer is also its attester.** SLSA states the fix:
provenance is generated by a trusted builder, not asserted by the producer. Two facts make this
urgent rather than academic:

- CI re-runs only L1. `template/.github/workflows/verify.yml` sets `CMP_DEVICE: none`, so an L2
  rung rests entirely on the file the author committed.
- Gatekeeper, the hosted notary ("checking is free; accountable attestation is the paid service",
  `docs/NORTH-STAR.md` §2), runs the same predicate over the PR's files and re-executes nothing. It
  can only attest what the committed file says.

NORTH-STAR G1 ("is there any state that only an agent's word supports?") answers yes today for
every rung, and G4 asks that a stranger can check "that this receipt attests these bytes" — which
the hash answers — without being able to check who produced them.

## Decision

1. **CI attests the receipt CI itself produced.** The template's `verify.yml` gains job permissions
   `contents: read, id-token: write, attestations: write` and, after the "Verify lane" step,
   `actions/attest-build-provenance@v2` over `qa/evidence/latest.json` (the path
   `qa/harness-manifest.json` names as the receipt). Signing is keyless: Sigstore issues a
   short-lived certificate bound to the workflow's OIDC identity, so no key exists that the
   receipt's producer could reach. `gh attestation verify <file> --repo <owner>/<repo>` then
   answers: *a GitHub-hosted run of this workflow produced this receipt from this commit.* The
   step runs on push and on same-repository pull requests; a fork's pull request is issued no
   id-token, so it is skipped there rather than failing the check.
2. **The L2 rung stays self-attested until CI runs the runtime tier, and the receipt's reader says
   so per rung.** `attestationStanding(receipt, { attestedThrough })` in
   `packages/receipts/src/receipt-validate.mjs` reports which rungs are CI-attested and which are
   self-attested; `qa/receipt-check.mjs` prints that line under `VALID`. It is a report and never a
   verdict — nothing it returns changes what any predicate decides.
3. **The marker lives outside the receipt.** The smallest honest mechanism is not a field. An
   attestation covers the receipt's bytes, so writing it into the receipt afterwards would change
   the bytes it covers; and any field the producer writes — `attestation`, `producedBy: "ci"`, a
   `GITHUB_ACTIONS` probe at write time — is the producer's word again, the exact gap this ADR
   closes (setting an environment variable is not an identity). So a rung counts as CI-attested
   only when a *caller* has verified an attestation outside the file and passes `attestedThrough`
   (the highest rung that verified receipt earned). `qa/receipt-check.mjs` reads only the committed
   file, verifies nothing, passes nothing, and therefore reports every rung self-attested. That is
   true, and it is the point.
4. **Gatekeeper checks the attestation for the rungs CI ran**, instead of trusting the committed
   file for them: fetch the attestation for the PR head's `verify-evidence` receipt, verify it,
   compare it with the committed receipt (per Consequences below), and pass `attestedThrough`. The
   Gatekeeper change is its own repository's slice; this ADR only fixes the contract it reads.
5. **Stamped apps get a recipe to make the check binding.** `template/qa/ruleset.json` is a GitHub
   ruleset requiring the Verify workflow's check on the default branch with no bypass actors;
   `template/README.md` carries the one `gh api` line that installs it. The check's context is
   `android` — the job's name, which is what GitHub reports — not the workflow's name `Verify`.

## Consequences

- **What "offline verification" (G4) means now.** It splits in two. *These bytes* — the receipt
  attests this tree — stays fully offline and from the repo alone: `inputs.hash` recompute, no
  network, unchanged. *This producer* — CI made this receipt — needs two things the repo does not
  hold: the attestation bundle (a Sigstore bundle: certificate, signature, transparency-log proof)
  and a Sigstore trusted root (the Fulcio CA and Rekor keys the certificate chains to). Both can be
  fetched once and the verification then runs offline against them
  (`gh attestation download`, then `gh attestation verify --bundle … --custom-trusted-root …` —
  **UNVERIFIED**: flag names to check against `gh attestation verify --help`). The trusted root
  rotates, so an offline check is as good as the snapshot it was given, and it must record which
  snapshot it used. G4's sentence therefore holds for the bytes and becomes "offline once the
  bundle and trust root are in hand" for the producer.
- **Private repositories.** Artifact attestations on public repositories are available on every
  plan and are logged to the public-good Sigstore instance. For **private** repositories,
  availability depends on the GitHub plan — understood at the time of writing to require GitHub
  Enterprise Cloud, with signing by GitHub's own Sigstore instance rather than the public one.
  **UNVERIFIED** — the check to run: GitHub's "Using artifact attestations" documentation,
  section on availability, and one `attest-build-provenance` run in a private repository on a
  non-Enterprise plan. Until it is checked, the template's step may fail on private repositories
  under Free/Pro/Team; if it does, the step needs a guard, not a removal.
- **The committed receipt and CI's receipt are different bytes.** `generatedAt`, durations and
  tool timings differ on every run, so the attestation does not cover the committed file and the
  comparison is never byte equality. It is: same `inputs.hash` (same verified tree), and for every
  step CI ran, the same verdict. Steps CI did not run (the L2 tier, SKIPped under
  `CMP_DEVICE: none`) are exactly the rungs that stay self-attested.
- **The local reader never says "CI-attested".** Every rung is self-attested at the Stop hook and
  at `node qa/receipt-check.mjs`, because the file on disk is the author's. The upgrade to
  "CI-attested" happens only where an attestation is verified — Gatekeeper, or a reviewer running
  `gh attestation verify`. Launch prose follows the same line: *the L1 check was CI-attested; the
  L2 verdict is the machine's word until CI runs that tier.*
- **No change to what the receipt hashes.** The surface, the schema and the predicate are
  untouched; ADR-0005 stands, and its "tamper-evident" consequence is read as "stale-evident,
  forge-evident only against a re-run" (KD-271).
- **Cost.** One more step per CI run (seconds) and three job permissions. A fork's pull request is
  unattested by construction.
- **Pinned major.** `@v2` pins the major, not a digest. **UNVERIFIED**: that `v2` is the current
  major and that its input is named `subject-path` — check the action's README before this ADR is
  accepted.

## Sub-proposal (not decided): step rows and an in-toto envelope

Recorded so that a later ADR can decide it; nothing here is built.

- **Step rows gain `exitCode` and `argv`.** Today a row carries `name`, `verdict`, `reason`,
  `note`, `durationMs`, `details`, `skipKind`, `layer` and `harness`, but no exit code and no
  command line (D-5). With both, an attested receipt says not only "CI ran step X and it passed"
  but what X was, which is what a verifier comparing two receipts needs.
- **The envelope maps to an in-toto Statement.** The receipt would be the predicate of a Statement
  whose envelope carries `_type`, `subject[].digest` (the receipt's or the tree's digest) and a
  `predicateType` URI in place of `schema: "prooflane-evidence/1"`. D-5 gives the field-by-field
  mapping and its gaps. **To verify against the in-toto Statement v1 specification before any field
  is named:** the exact `_type` URI, the digest-map key names, and whether `verdict`/`steps` belong
  in a sibling predicate rather than SLSA provenance. No predicate field names are proposed here.
- **Why this is a proposal, not a re-litigation.** On 2026-09-03 a cross-stack programme that
  included in-toto was rejected because "the standards carried no repo file:line showing the gap"
  (`docs/EVIDENCE-ECONOMICS-PLAN.md`, the 2026-09-03 entry, ~line 386). Finding D-1 is that
  file:line: `packages/receipts/src/receipt-validate.mjs` (the verdict "the hash cannot cover")
  and `packages/receipts/src/inputs-hash.mjs` (the exclusion of `qa/evidence`).
