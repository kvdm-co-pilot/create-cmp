# Harness engineering and context engineering for long-running coding agents (state as of 2026-09-27)

Scope note for the writer: "harness" here means everything around the model in an agentic-coding system — the agent loop, tools, context management (compaction, editing, memory), permissions/hooks, sub-agent orchestration, session persistence and verification loops. Anthropic-first-party material is the spine; external material is included where Anthropic staff cite it, where it names the discipline, or where it supplies measurements Anthropic does not publish. Every date below is the source's own publication date. Items marked SUPERSEDED were current guidance at the time and have since been replaced by a newer Anthropic statement.

A caution on secondary sources: the Marmelab "State of AI Harness Engineering 2026" survey (2026-09-24) mis-dates the Anthropic posts (it lists "Effective harnesses" as September 2025 and "Harness design" as November 2025; the primary pages say 2025-11-26 and 2026-03-24 respectively). Dates in these notes come from the primary pages wherever one was fetched.

## Key Question 1 — Anthropic "Effective context engineering for AI agents" (Sept 2025): rules, and whether it has been updated in 2026

### Takeaway
The post (2025-09-29) defines context engineering as curating "the smallest set of high-signal tokens that maximize the likelihood of your desired outcome", grounds it in "context rot", and prescribes just-in-time retrieval, compaction, structured note-taking (memory) and sub-agent isolation. The post itself carries no 2026 revision, but its recommendations have been operationalised and partly superseded by 2026 platform features (server-side compaction, GA memory tool, 1M default windows, context awareness tags).

### Cited Findings
- Published 2025-09-29 by Anthropic's Applied AI team (Prithvi Rajasekaran, Ethan Dixon, Carly Ryan, Jeremy Hadfield, with Rafi Ayub, Hannah Moran, Cal Rueb, Connor Jennings). — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Definition: context engineering is "the set of strategies for curating and maintaining the optimal set of tokens (information) during LLM inference, including all the other information that may land there outside of the prompts"; it is "iterative and the curation phase happens each time we decide what to pass to the model." — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Context rot / attention budget: "As the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases"; the cause is the transformer's "n² pairwise relationships for n tokens" and a training distribution that favours shorter sequences. The post cites Chroma's needle-in-a-haystack work, the Transformer paper (arXiv 1706.03762) and position-interpolation work (arXiv 2306.15595). — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- System prompts should sit at the "right altitude": neither "overly complex, hardcoded logic" nor "vague high-level guidance"; use XML/Markdown sections; pursue "the minimal set of information that fully outlines your expected behavior." — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Tools: "self-contained, robust to error, and extremely clear with respect to their intended use"; avoid "bloated tool sets"; "If a human engineer can't definitively say which tool should be used in a given situation, an AI agent can't be expected to do better." — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Examples: "curate a set of diverse, canonical examples" rather than enumerating edge cases. — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Just-in-time retrieval: keep "lightweight identifiers (file paths, stored queries, web links, etc.)" and load data at runtime; Claude Code "can write targeted queries, store results, and leverage Bash commands like head and tail to analyze large volumes of data without ever loading the full data objects into context." Hybrid model: "CLAUDE.md files are naively dropped into context up front, while primitives like glob and grep allow it to navigate its environment and retrieve files just-in-time." Trade-off acknowledged: "Runtime exploration is slower than retrieving pre-computed data." — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Compaction: "taking a conversation nearing the context window limit, summarizing its contents, and reinitiating a new context window with the summary"; "The art of compaction lies in the selection of what to keep versus what to discard"; tune by "maximizing recall ... then iterate to improve precision"; "One of the safest lightest touch forms of compaction is tool result clearing." — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Structured note-taking: agents "regularly write notes persisted to memory outside of the context window"; Claude-plays-Pokémon example ("for the last 1,234 steps I've been training my Pokémon in Route 1..."); the memory tool launched "in public beta" alongside Sonnet 4.5 (SUPERSEDED — see KQ3: the memory tool no longer requires a beta header). — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Sub-agent architectures: each sub-agent "might explore extensively, using tens of thousands of tokens or more, but returns only a condensed, distilled summary of its work (often 1,000-2,000 tokens)." — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Closing rule: "do the simplest thing that works"; "treating context as a precious, finite resource will remain central to building reliable, effective agents." — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- 2026 platform docs still point to this post as the canonical explanation: the Context windows page says "As token count grows, accuracy and recall degrade, a phenomenon known as context rot" and links to it; the Memory tool page says "Memory supports just-in-time context retrieval" and links to it. — [Context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows); [Memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- The 2025-06-13 multi-agent research post is the earlier source for the sub-agent token numbers: "agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens as chats"; "token usage by itself explains 80% of the variance" in BrowseComp; lead agent saves "its plan to Memory to persist the context, since if the context window exceeds 200,000 tokens it will be truncated." — [Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)

### Inferences
- The post's three long-horizon techniques (compaction, memory notes, sub-agents) map one-to-one onto 2026 first-party features: server-side compaction, the `memory_20250818` tool, and Agent SDK subagents. The prose has not been re-issued; the features are the update.
- The "200k truncation" constraint that motivated the 2025 memory-handoff pattern no longer holds on 1M-window models (KQ3), but Anthropic's 2026 guidance (KQ2) still favours resets over filling the window, so the pattern survives for quality reasons rather than capacity reasons.

### Gaps
- No "updated on" stamp was found on the post; I could not confirm whether Anthropic silently edited it in 2026.
- The post's Chroma "context rot" citation was not fetched; its exact numbers are not reproduced here.

## Key Question 2 — Anthropic "Effective harnesses for long-running agents" (Nov 2025) and 2026 follow-ups: exact recommendations

### Takeaway
The 2025-11-26 post prescribes an initializer-agent/coding-agent split with three artifacts (init.sh, a progress file, a JSON feature list) plus a fixed session-start ritual, one feature per session, git-clean handoffs and browser-based end-to-end self-verification. The 2026-03-24 follow-up ("Harness design for long-running application development") extends it into a planner/generator/evaluator harness, names "context anxiety", and reports that context resets with structured handoff artifacts beat compaction — then partially walks the complexity back for Opus 4.6.

### Cited Findings
- Published 2025-11-26, written by Justin Young with David Hershey, Prithvi Rajasekaran, Jeremy Hadfield and others. — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Three observed failure modes: agents try to "one-shot the app" and run out of context mid-implementation; agents declare the project done after partial progress; later sessions inherit half-implemented features without context. — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Two roles: an initializer agent (first session) and a coding agent (every later session). — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Initializer outputs: `init.sh` (dev-server startup), `claude-progress.txt` (activity log), and a feature-list JSON; the claude.ai-clone demo had "over 200 features, such as 'a user can open a new chat, type in a query, press enter, and see an AI response'", all starting at `"passes": false`. — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- JSON over Markdown: "We landed on using JSON for this, as the model is less likely to inappropriately change or overwrite JSON files compared to Markdown files." — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Session-start ritual: run `pwd`; read progress notes and git log; pick the highest-priority incomplete feature; run `init.sh`; run an end-to-end smoke test before new work. — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- One feature at a time: "The next iteration of the coding agent was then asked to work on only one feature at a time." — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Clean-state handoff: "descriptive commit messages and ... write summaries of its progress in a progress file. This allowed the model to use git to revert bad code changes." — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Self-verification: Puppeteer MCP browser automation; "Claude mostly did well at verifying features end-to-end once explicitly prompted to use browser automation tools and do all testing as a human user would"; the mitigated failure was "Claude's tendency to mark a feature as complete without proper testing." — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Scope: "This demo is optimized for full-stack web app development"; code in the quickstart repo. — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents); [anthropics/claude-quickstarts autonomous-coding](https://github.com/anthropics/claude-quickstarts/tree/main/autonomous-coding)
- The pattern is now codified in platform docs as the "Multisession software development pattern": initializer session sets up "a progress log ... a feature checklist ... and a reference to any startup or initialization script"; each session opens by reading them; end-of-session update; "Work on one feature at a time. Mark a feature complete only after end-to-end verification confirms it works, not when the code is written." — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- The API now injects a memory protocol automatically when the memory tool is present: "ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE ... ASSUME INTERRUPTION: Your context window might be reset at any moment, so you risk losing any progress that is not recorded in your memory directory." — [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- 2026-03-24 follow-up "Harness design for long-running application development" by Prithvi Rajasekaran (Labs): models "wrap up work prematurely" near perceived context limits ("context anxiety"); "Claude Sonnet 4.5 exhibited context anxiety strongly enough that compaction alone wasn't sufficient", so the harness used "context resets—clearing the context window entirely" with structured handoffs; compaction "preserves continuity" but "doesn't give the agent a clean slate." — [Anthropic Engineering (URL as cited by a mirror; primary not directly fetched)](https://www.anthropic.com/engineering/harness-design-long-running-apps); [mirror note](https://github.com/celesteanders/harness/blob/main/docs/research/260324_anthropic_harness_design.md)
- Planner/generator/evaluator roles; generator and evaluator agree "a sprint contract: agreeing on what 'done' looked like" before each unit; evaluator does QA via Playwright. Self-grading fails because agents "respond by confidently praising the work—even when, to a human observer, the quality is obviously mediocre"; an external evaluator is "far more tractable" to tune toward skepticism. — [mirror note of the 2026-03-24 post](https://github.com/celesteanders/harness/blob/main/docs/research/260324_anthropic_harness_design.md)
- Numbers from that post: Retro Game Maker on Opus 4.5 — solo agent 20 min / $9 with broken mechanics vs full harness 6 h / $200 with working gameplay; DAW on Opus 4.6 with a simplified harness — 3 h 50 min, $124.70. With Opus 4.6 ("plans more carefully, sustains agentic tasks for longer") the team removed sprints and kept planner + evaluator only where task complexity exceeded baseline capability, citing "find the simplest solution possible, and only increase complexity when needed" from Building Effective Agents. — [mirror note](https://github.com/celesteanders/harness/blob/main/docs/research/260324_anthropic_harness_design.md); [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- 2026-02-05 "Building a C compiler with a team of parallel Claudes" (Nicholas Carlini): 16 parallel agents, "nearly 2,000 Claude Code sessions", "just under $20,000", 100k lines of Rust compiling Linux 6.9; an infinite-loop harness ("When it finishes one task, it immediately picks up the next"); task claiming by "writing a text file to current_tasks/" where "git's synchronization forces the second agent to pick a different one"; "it's important that the task verifier is nearly perfect, otherwise Claude will solve the wrong problem"; "I had to constantly remind myself that I was writing this test harness for Claude and not for myself" (reduce output verbosity, log to queryable files, `--fast` modes, "extensive READMEs and progress files"). Ceilings: agents "would hit the same bug, fix that bug, and then overwrite each other's changes" at 99% pass; "New features and bugfixes frequently broke existing functionality"; Claude once ran `pkill -9 bash` and killed its own loop. — [Anthropic Engineering](https://www.anthropic.com/engineering/building-c-compiler)
- 2026-06-02 "A harness for every task: dynamic workflows in Claude Code" (Thariq Shihipar, Sid Bidasaria): "Claude can now write and orchestrate its own multi-agent harness on the fly" via a JavaScript Workflow environment (`agent()`, `parallel()`, `pipeline()`); motivating single-context failure modes: "agentic laziness", "self-preferential bias", "goal drift"; six patterns (classify-and-act, fan-out-and-synthesize, adversarial verification, generate-and-filter, tournament, loop-until-done); examples of 14 agents / 482k tokens / 6m12s and 22 agents / 1.1M tokens / 11m03s. — [Claude blog](https://claude.dev/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code/)
- The context-windows doc now tells multi-session builders to "design your state artifacts so that context recovery is fast when a new session starts" and links both the memory-tool pattern and the Nov 2025 post. — [Context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows)

### Inferences
- Across Nov 2025 → Mar 2026 → Jun 2026 the constant is "done" defined outside the worker's own judgment: a JSON feature list flipped only after E2E verification (Nov), a negotiated sprint contract judged by a fresh-context evaluator (Mar), adversarial-verification/tournament patterns (Jun). Self-assessment is the named weak point every time.
- Anthropic's own trajectory is to add harness structure when the model falls short and remove it as models improve (sprints dropped for Opus 4.6). Harness components are therefore versioned against model capability, not permanent.
- The JSON-over-Markdown rationale (models less likely to overwrite JSON) is an early, first-party statement that machine-readable state should be the "definition of done" ledger.

### Gaps
- The 2026-03-24 post was not fetched from anthropic.com (my URL guess 404'd); content is via a mirror that quotes it and gives the URL `/engineering/harness-design-long-running-apps`. Verify the URL before citing externally.
- No first-party success-rate or feature-count statistics were published for the Nov 2025 claude.ai-clone run beyond ">200 features".

## Key Question 3 — What Anthropic says about compaction, context windows (200k vs 1M), the memory tool, context editing and prompt caching economics (platform docs)

### Takeaway
As of 2026-09-27: 1M tokens is the default window at standard pricing for Opus 4.6+/Sonnet 4.6+/Fable/Mythos (200k remains for Sonnet 4.5 and older); server-side compaction is the "primary strategy" and now comes in two betas (threshold `compact_20260112` and the newer on-demand `compact-2026-09-04`), with client-side SDK compaction deprecated; context editing (`context-management-2025-06-27`) clears tool results/thinking by rule; the memory tool (`memory_20250818`) is on all Claude 4+ models without a beta header; cache reads cost 0.1× base (0.05× on Opus 5.5, 0.025× on Fable 5.1) versus 1.25×/2× writes.

### Cited Findings
- Context sizes: "Claude Fable 5.1, Claude Mythos 5.1, Claude Fable 5, Claude Mythos 5, Claude Opus 5.5, Claude Opus 5, Claude Opus 4.8, Claude Opus 4.7, Claude Opus 4.6, Claude Sonnet 5, Claude Sonnet 4.6, and Claude Mythos Preview have a 1M-token context window ... Other Claude models, including Claude Sonnet 4.5, have a 200k-token context window." "For every model with a 1M-token context window, 1M is the default: you don't need a beta header, and long-context requests are billed at standard pricing." Max output 128k. — [Context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows)
- "more context isn't automatically better ... This makes curating what's in context just as important as how much space is available." "Cached prompt prefixes still occupy the context window: prompt caching changes what you pay for those tokens, not whether they count." — [Context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows)
- Context awareness: Sonnet 5 / 4.6 / 4.5 and Haiku 4.5 receive an injected `<budget:token_budget>` in the system prompt and `<system_warning>Token usage: 35000/200000; 165000 remaining</system_warning>` after each tool call; "Claude Opus 4.7 and later Opus models, Claude Fable 5.1, Claude Mythos 5.1, Claude Fable 5, and Claude Mythos 5 don't receive these injected tags" — use task budgets (beta) instead. — [Context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows)
- Overflow: on Claude 4.5+ generation reaching the window stops with `stop_reason: "model_context_window_exceeded"`; input alone over the window returns 400 "prompt is too long". — [Context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows)
- Compaction: "Compaction replaces the older turns of a conversation with a summary that Claude writes on the server ... it keeps the active context small, because response quality degrades as a conversation grows." Two variants: on demand (beta header `compact-2026-09-04`, top-level `compaction` parameter, returns a signed `compaction` block with `stop_reason: "compaction"`) and threshold (`compact_20260112`, one parameter, API drops what came before). "Use on-demand compaction wherever it is available." — [Compaction overview](https://platform.claude.com/docs/en/build-with-claude/compaction); [Compaction on demand](https://platform.claude.com/docs/en/build-with-claude/compaction-on-demand)
- On-demand details: summariser "uses the request's model, system, tools, thinking settings, and max_tokens"; custom `instructions` up to 16,384 chars replace the default prompt; billed like any request under `usage.iterations`; "Sending a block back on later requests adds no compaction cost"; `cache_control` on the block "places a breakpoint after the summary"; images/documents/fetched URLs inside the summarised range "are gone"; mid-conversation `role: "system"` instructions are summarised away and must be restated; cannot combine `compaction` with `context_management`. Supported: Fable 5.1/5, Mythos 5.1/5/Preview, Opus 5.5/5/4.8/4.7/4.6, Sonnet 5/4.6; not on Bedrock. — [Compaction on demand](https://platform.claude.com/docs/en/build-with-claude/compaction-on-demand)
- Client-side compaction in the SDKs is "Deprecated: Anthropic recommends server-side compaction instead." — [Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)
- Context editing (beta `context-management-2025-06-27`): `clear_tool_uses_20250919` (defaults: trigger 100,000 input tokens, keep 3 tool uses; options `clear_at_least`, `exclude_tools`, `clear_tool_inputs`) and `clear_thinking_20251015` (per-model defaults; Opus 4.5+/Sonnet 4.6+/Fable/Mythos keep all prior thinking). Clearing "invalidates cached prompt prefixes"; use `clear_at_least` "to ensure minimum tokens cleared, making cache invalidation worthwhile." Available on all supported models. — [Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)
- Memory tool: `{"type": "memory_20250818", "name": "memory"}`; client-side, six commands (view, create, str_replace, insert, delete, rename) under `/memories`; "available on all Claude 4 and later models"; "the memory tool itself doesn't require a beta header" (SUPERSEDES the Sept 2025 "public beta" statement); "For long-running agents, consider using both: compaction keeps the active context small without client-side bookkeeping, and memory preserves the information that must survive summarization." Security: path-traversal validation is the implementer's job. — [Memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Prompt caching pricing: 5-minute cache write 1.25× base input, 1-hour write 2×, cache read 0.1× — "Claude Opus 5.5 uses 0.05x ... Claude Fable 5.1/Mythos 5.1 use 0.025x". Minimum cacheable prefix 512 tokens (Opus 5.5, Fable, Mythos, Opus 5), 1,024 (Opus 4.8, Sonnet 5, Sonnet 4.6, Opus 4.1), 2,048 (Opus 4.7), 4,096 (Haiku 4.5). Up to 4 explicit breakpoints; a top-level `cache_control` enables automatic caching where "the cache breakpoint advances automatically." Cache invalidators: tool-definition changes (complete miss), web-search/citations toggles, fast mode, `tool_choice`, images, thinking/effort changes. Worked example: 83% input-cost reduction for a 5k-token prompt reused 10 times. — [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Claude Code's caching layer order: system prompt (instructions, tool definitions) → project context (CLAUDE.md, auto memory) → conversation; "A change to the system prompt invalidates everything." Invalidators in Claude Code: model switch, effort change (except Opus 5.5/Fable 5.1 on API/subscription), fast mode, MCP server connect/remove when tools are in the prefix, denying an entire tool, compaction, image pruning, upgrades. Cache-safe: file edits, CLAUDE.md edits (don't apply until `/clear`/`/compact`/restart), permission-mode changes, skills, `/rewind`, subagent spawn. — [Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching)
- TTL in Claude Code: main conversation gets one hour on a subscription within plan usage, five minutes on usage credits/API key/cloud; subagents, workflows, compaction get five minutes unless `promptCacheTtl` / `subagentPromptCacheTtl` set. — [Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching)
- 2026-04-30 "Lessons from building Claude Code: prompt caching is everything" (Thariq Shihipar): "Long running agentic products like Claude Code are made feasible by prompt caching"; "static content first, dynamic content last"; plan mode implemented via "EnterPlanMode and ExitPlanMode as tools themselves" so the prefix is not disturbed; MCP tools sent as "lightweight stubs (just the tool name, with `defer_loading: true`)"; compaction must reuse the parent's prefix because otherwise "the prefixes diverge at the very first token"; the team runs "alerts on our prompt cache hit rate and declare SEVs if they're too low." — [Claude blog](https://claude.dev/blog/lessons-from-building-claude-code-prompt-caching-is-everything/)

### Inferences
- Anthropic's 2026 stack has a clear preference order for staying inside the window: (1) keep the prefix stable and cached, (2) clear tool results/thinking by rule (cheap, but a cache write), (3) compact on demand at a natural break, (4) persist state to memory files so a full reset is survivable. Every step trades a one-time cache rebuild for a smaller ongoing per-step bill.
- The removal of the 200k truncation ceiling on Opus 4.6+ moved the compaction decision from a hard limit to a quality/cost judgment, which is why the docs now stress "curating what's in context" over capacity.

### Gaps
- The Opus 4.6 system card PDF exceeded the fetch size limit; its exact scaffold-disclosure text is not quoted here (see KQ6 for the Sonnet 4.5 equivalent).
- I did not fetch the pre-2026 1M-beta pricing page, so the claim that a long-context premium once applied above 200k is not sourced here; the current page's "standard pricing" is what is cited.

## Key Question 4 — How the Claude Agent SDK defines the harness (agent loop, hooks, permission modes, subagents, MCP, sessions, compaction) and what changed in 2026

### Takeaway
The SDK describes itself as "the same tools, agent loop, and context management that power Claude Code" and documents the loop as receive → evaluate → execute tools (hookable) → repeat until no tool calls → result, with `max_turns`/`max_budget_usd`, six permission modes (incl. `auto` and `dontAsk`), lifecycle hooks (incl. `PreCompact`, `Stop`), fresh-context subagents and automatic compaction that emits a `compact_boundary` message. 2026 changes are incremental hardening: session fork/resume-at-entry, `terminal_reason`, `verbatim_prompts`, system-prompt snapshots for cache reuse, MCP 2.x, and auto mode becoming the default permission mode on paid plans from 2026-08-14.

### Cited Findings
- "The Agent SDK gives you the same tools, agent loop, and context management that power Claude Code, programmable in Python and TypeScript." Capabilities table: built-in tools, hooks, subagents, MCP, permissions, sessions ("Maintain context across exchanges, resume or fork later"), skills/commands/memory loaded from `.claude/`, plugins. Managed Agents is described as "A hosted agent harness that runs the agent loop." — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- The loop: "Claude evaluates your prompt, calls tools to take action, receives the results, and repeats until the task is complete." Steps: receive prompt (yields `SystemMessage` init) → evaluate → execute tools ("You can use hooks to intercept, modify, or block tool calls before they run") → repeat ("Each full cycle is one turn") → `ResultMessage` "with the final text, token usage, cost, and session ID." — [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- Stop controls: `max_turns` (tool-use turns only) and `max_budget_usd` ("Setting a budget is a good default for production agents"); budget covers subagents; result subtypes `success`, `error_max_turns`, `error_max_budget_usd`, `error_during_execution`, `error_max_structured_output_retries`; `effort` levels low/medium/high/xhigh/max. — [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- Permission modes: `default`, `acceptEdits`, `plan`, `dontAsk` ("every call that would otherwise prompt is denied"), `auto` ("Uses a model classifier to approve or deny permission prompts"), `bypassPermissions` ("Use only in isolated environments"). Allow/deny rules like `"Bash(npm *)"`. Read-only tools run in parallel; mutating tools run sequentially. — [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- Hooks: `PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `Stop`, `SubagentStart`/`SubagentStop`, `PreCompact`; "Hooks run in your application process, not inside the agent's context window, so they don't consume context"; a `PreToolUse` rejection "prevents it from executing, and Claude receives the rejection message instead." — [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- Context and compaction: "It does not reset between turns within a session. Everything accumulates"; static content is prompt-cached; "When the context window approaches its limit, the SDK automatically compacts the conversation ... emits a message with `type: "system"` and `subtype: "compact_boundary"`"; "Persistent rules belong in CLAUDE.md ... because CLAUDE.md content is re-injected on every request"; customise via a summary-instructions section in CLAUDE.md, a `PreCompact` hook, or sending `/compact`. — [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- Subagents: "Each subagent starts with a fresh conversation ... only its final response returns to the parent as a tool result." Sessions: resume, continue, fork; `session_store` adapter for stateless hosts (dual-write). — [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)

## Key Question 5 — Community/industry definitions of "harness engineering" and where they agree/disagree with Anthropic

### Takeaway
The term was popularised by Mitchell Hashimoto (2026-02-05: "anytime you find an agent makes a mistake, you take the time to engineer a solution such that the agent never makes that mistake again"), named as a discipline by OpenAI's Ryan Lopopolo (2026-02-11), and formalised by Thoughtworks' Birgitta Böckeler as "Agent = Model + Harness" (2026-04-02). All agree that mechanical enforcement (tests, linters, hooks) beats prose and that context must be curated; they diverge on whether AI reviewers help, how many hand-offs to allow, and whether to put rules in the harness or in the model's judgment.

### Cited Findings
- Hashimoto, "My AI Adoption Journey", 2026-02-05: harness engineering is "the idea that anytime you find an agent makes a mistake, you take the time to engineer a solution such that the agent never makes that mistake again"; two forms — an AGENTS.md where "Each line in that file is based on a bad agent behavior, and it almost completely resolved them all", and "scripts to take screenshots, run filtered tests, etc etc." Six adoption stages ending in "Engineer the Harness" and "Always Have an Agent Running". — [mitchellh.com](https://mitchellh.com/writing/my-ai-adoption-journey)
- OpenAI, "Harness engineering: leveraging Codex in an agent-first world", 2026-02-11, Ryan Lopopolo: ~1M lines of code in a five-month experiment with a small team and zero hand-written source; practices — `docs/` as the agent knowledge base, dependency layers "Types → Config → Repo → Service → Runtime → UI" enforced by custom linters, structural tests and CI, observability (logs/metrics/spans) the agent reads to reproduce bugs, PR/CI feedback loops. Fowler summarised it as "context engineering, architectural constraints, and garbage collection." — [InfoQ report (primary returned 403)](https://www.infoq.com/news/2026/02/openai-harness-engineering-codex/); primary: [OpenAI](https://openai.com/index/harness-engineering-leveraging-codex-in-an-agent-first-world/)
- OpenAI, "Codex as a platform: build on the open agent harness", 2026-08-19: "the most valuable reusable asset inside Codex is not the chat interface. - Böckeler (martinfowler.com), 2026-04-02 (from a 2026-02-17 memo): "Agent = Model + Harness"; distinguishes the builder's harness from the user's harness; controls are Guides (feedforward: architecture.md, linters, LSP) and Sensors (feedback: tests, review agents, static analysis), each "computational" (deterministic, fast) or "inferential" (semantic, slow); behaviour is "the elephant in the room"; "A good harness should not necessarily aim to fully eliminate human input, but to direct it to where our input is most important." ## Key Question 6 — Measurable evidence that harness design changes outcomes independent of the model

### Takeaway
Same-model, different-harness comparisons in 2026 consistently show large efficiency swings (up to ~40× tokens per solved task) and moderate-to-large pass-rate swings (0–8 pp in one controlled study, 20 pp in another), and Anthropic's own disclosures show it reports benchmarks with a deliberately minimal two-tool scaffold precisely because scaffold choice moves the number.

### Cited Findings
- Anthropic scaffold disclosure (Sonnet 4.5 launch, 2025-09-29): "All Claude results were reported using a simple scaffold with two tools—bash and file editing via string replacements"; prompt addition "You should use tools as much as possible, ideally more than 100 times"; high-compute variants sample parallel attempts, discard patches failing visible tests and pick with an internal scorer; Terminal-Bench used "the default agent framework (Terminus 2), with XML parser, averaging multiple runs during different days." — [Anthropic news](https://www.anthropic.com/news/claude-sonnet-4-5)
- Anthropic's original SWE-bench engineering post: "give as much control as possible to the language model itself, and keep the scaffolding minimal" — the agent has a prompt, a Bash tool and an Edit tool. — [Anthropic Engineering](https://www.anthropic.com/engineering/swe-bench-sonnet)
- Terminal-Bench 2.0 (arXiv 2601.11868, 2026-01-17, ICLR 2026; Merrill, Shaw, Carlini et al.): 89 tasks; "frontier models and agents score less than 65%"; run under the Harbor harness supporting Claude Code, Codex CLI, OpenHands, Mini-SWE-Agent and Terminus 2 ("a neutral testbed"). Search-summary numbers: Codex CLI + GPT-5.2 63% vs Terminus 2 + Claude Opus 4.5 58%; Opus 4.5/Terminus 2 used 3.9M input / 1.3M output tokens versus 137.5M input for GPT-5.2/Codex CLI; most trials "under 20 minutes, using fewer than 25 model calls and 10 million tokens", extremes "up to 2 hours ... nearly 100 million tokens." — [arXiv](https://arxiv.org/abs/2601.11868); [tbench.ai](https://www.tbench.ai/)
- "The Scaffold Effect in Coding Agents" (Vats, Golev; arXiv 2607.22585): a harness is "the scaffold that issues tools, manages context, and decides when to stop"; across Goose, OpenCode and OpenHands-SDK on a 50-task Terminal-Bench Pro subset, "up to a 40x difference in tokens per solved task" for the same model, pass-rate gaps of "0-8 percentage points" (most CIs include zero), and harness-specific "failure fingerprints" (Goose: REASON; OpenHands-SDK: VERIFY/MAX_TURNS; OpenCode: idle-loop/TIME). Recommends reporting tokens, latency and full harness spec with every model comparison. — [arXiv](https://arxiv.org/abs/2607.22585)
- "An Empirical Study of Harness Design for Coding Agents" (Fan et al.; arXiv 2609.20804, 2026-09-17): fixed loop, varied planning / action space / context management across four models, SWE-bench Verified and Terminal-Bench 2.1, 176 matched settings. Findings: most context-management benefit comes from "preventing context-overflow failures", with rule-based filtering before LLM summarisation most efficient; planning shifts "from accuracy improvement for weaker models to cost reduction for stronger models"; predefined tools help weaker-bash models while capable models get "substantially lower cost" with bash-only. — [arXiv](https://arxiv.org/abs/2609.20804)
- Composio (2026-08-04): Kimi K3 held constant across eight harnesses on 25 tasks — pass rates from 68% (Codex, 17/25) to 88% (Oh My Pi, 22/25); Claude Code 19/25 at the highest cost ($35.37, $1.96 per success vs Hermes Agent $0.46); tokens ranged ~2× (Kimi Code 15.27M); tool calls 223–402 "without proportional success gains". — [Composio](https://composio.dev/content/best-ai-agent-harnesses)
- Anthropic's own harness ablations (KQ2): Retro Game Maker solo vs harness (20 min/$9 broken vs 6 h/$200 working) on the same Opus 4.5; the multi-agent research system beat single-agent Opus 4 by 90.2% on internal evals. — [mirror of 2026-03-24 post](https://github.com/celesteanders/harness/blob/main/docs/research/260324_anthropic_harness_design.md); [Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)
- Related 2026 benchmarks devoted to the harness variable: Harness-Bench (arXiv 2605.27922), LoopsBench (2608.00267), Long-Horizon-Terminal-Bench (2607.08964), Claw-SWE-Bench (2606.12344). — [arXiv](https://arxiv.org/abs/2605.27922); [arXiv](https://arxiv.org/pdf/2608.00267); [arXiv](https://arxiv.org/html/2607.08964v1); [arXiv](https://arxiv.org/pdf/2606.12344)

### Inferences
- The robust, replicated finding is that harness choice moves cost far more than pass rate for strong models (40× tokens vs ≤8 pp in the controlled study); pass-rate gaps of 20 pp appear when tasks are realistic business workflows rather than curated benchmark items. For a delivery harness the lever with the strongest evidence is therefore verification-and-stop discipline and context hygiene, not extra reasoning scaffolding.

## Key Question 7 — Token/cost economics of harnesses: cache reads vs writes, steps × context, when to hand off to a fresh session

### Takeaway
Anthropic's economics are explicit: every step re-sends the whole prefix, so cost ≈ Σ(steps × context) at the cached rate plus full price for whatever changed; cache reads are 0.1× (as low as 0.025× on Fable 5.1) while writes are 1.25–2×; anything that breaks the prefix (model/effort/tool-set change, compaction) is a one-time full re-read. The recommended discipline is `/clear` between unrelated tasks, compact at natural breaks (never mid-task), offload verbose work to subagents/hooks, and keep static context (CLAUDE.md under ~200 lines) at the front.

### Cited Findings
- Per-step re-send: "Claude Code sends your full conversation with every request, and each time Claude uses tools it sends another request carrying that batch of tool results. With prompt caching, Claude Code re-reads that history at the cached token rate, so a one-line question in a session that has been open all day still draws usage for the whole conversation." — [Manage costs](https://code.claude.com/docs/en/costs)
- Cache miss after idle: "your first message after a break longer than the cache lifetime misses the cache and reprocesses your full context. The lifetime is an hour on a subscription and drops to five minutes once you're drawing on usage credits; on an API key or cloud provider, it's five minutes by default." — [Manage costs](https://code.claude.com/docs/en/costs)
- `/clear` vs `/compact`: "`/compact` reads the conversation it summarizes, so compacting a large context is itself a large request. When you want a fresh start instead of continuity, `/clear` costs nothing." "Clear between tasks ... Stale context wastes tokens on every subsequent message." — [Manage costs](https://code.claude.com/docs/en/costs)
- Warm vs cold compaction: "While the cache is warm, that request reads your prefix from the cache, so a mid-session `/compact` costs a fraction of what the context size suggests ... After a break longer than the cache lifetime ... the summarization request reprocesses the full history as uncached input. This is why `/compact` costs the most when you resume an old session." Advice: "run `/compact` at a natural break in your work, such as between tasks, instead of waiting for auto-compaction to trigger mid-task"; `/rewind` "truncates back to a prefix that is already cached, rather than building a new one." — [Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching)
- "Pick your model and effort level at the top of a session, then save `/compact` for natural breaks between tasks. The fewer changes you make mid-task, the higher your cache hit rate." — [Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching)
- Rates: cache read 0.1× base (Opus 5.5 0.05×; Fable 5.1 / Mythos 5.1 0.025×); 5-min write 1.25×; 1-h write 2×; example Opus 5.5 base $4/MTok, 5m write $5/MTok, read $0.20/MTok. — [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Subagents as cost isolation: "Delegate these to subagents so the verbose output stays in the subagent's context while only a summary returns"; the SDK: "The main agent's context grows by that summary, not by the full subtask transcript." Subagents do not share the parent's cache ("Its first request doesn't read the parent's cache, because the two prefixes differ") and get a 5-minute TTL by default; a fork "inherits the parent's system prompt, tools, and conversation history exactly, so its first request reads the parent's cache." — [Manage costs](https://code.claude.com/docs/en/costs); [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop); [Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching)
- Hooks as pre-filters: "Instead of Claude reading a 10,000-line log file to find errors, a hook can grep for `ERROR` and return only matching lines, reducing context from tens of thousands of tokens to hundreds." — [Manage costs](https://code.claude.com/docs/en/costs)
- Scale multipliers: agents ~4× chat tokens, multi-agent ~15× (2025-06-13); agent teams "approximately 7x more tokens than standard sessions"; dynamic workflow examples 482k tokens for 14 agents, 1.1M for 22. — [Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system); [Manage costs](https://code.claude.com/docs/en/costs); [Claude blog](https://claude.dev/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code/)
- Average enterprise spend: "around $13 per developer per active day and $150-250 per developer per month, with costs remaining below $30 per active day for 90% of users"; "Unexpectedly high spend ... usually traces back to long sessions that were never cleared or to Opus left as the default model." — [Manage costs](https://code.claude.com/docs/en/costs)
- Auto-compaction threshold is model-dependent and tunable (`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`); on-demand API compaction guidance: estimate the next request as `input_tokens + cache_read_input_tokens + cache_creation_input_tokens + output_tokens` and "compact before you outgrow it, not after." — [community guide](https://bogdanmatasaru.github.io/claude-code-guide/guides/auto-compact); [Compaction on demand](https://platform.claude.com/docs/en/build-with-claude/compaction-on-demand)
- Observability: `/usage` shows a `Prompt cache (main)` line with hit share, misses and likely cause (e.g. `likely cause: tool definitions changed`); Claude Code counts a miss when a request re-processed ">5% and at least 2,000 tokens" of cacheable prefix; per-request fields `cache_creation_input_tokens` / `cache_read_input_tokens`. — [Manage costs](https://code.claude.com/docs/en/costs); [Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching)

### Inferences
- The "steps × context" cost model is stated in Anthropic's own words (full conversation on every request, cached). Marginal cost of one more tool call at context C is ≈ 0.1×C (or 0.025×C on Fable 5.1) plus the new tokens, so halving the resident context halves the per-step bill even with perfect caching; hence Anthropic's preference for `/clear`/fresh sessions between units of work over long continuous sessions.
- Anthropic gives no numeric "hand off at N tokens" rule; its rule is structural — hand off at the boundary of a unit of work, when the cache is warm, and never let auto-compaction fire mid-task. Fresh-session hand-off is cheapest when state has already been externalised (progress file, memory, git), which is exactly the Nov 2025 pattern.

### Gaps
- No first-party statement gives a percentage threshold for auto-compaction; the `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` figure comes from a community guide.
- Anthropic publishes no cache-hit-rate targets (the Apr 2026 post says they alert on it but withholds numbers).

## Key Question 8 — Implications for a Claude Code plugin repo ("a delivery harness that holds coding agents to a machine-enforced definition of done")

### Takeaway
Anthropic's 2025–2026 guidance validates the thesis directly — the "done" ledger should be machine-readable and flipped only by verification, the enforcement point should be hooks (deterministic, out-of-context, able to veto), and the session should be organised as one unit of work with externalised state — while the measured evidence says the biggest wins from a harness are in stop/verify discipline and context hygiene, not extra reasoning layers.

### Cited Findings
- "Done" as data: JSON feature list with `"passes": false` because "the model is less likely to inappropriately change or overwrite JSON files compared to Markdown files"; "Mark a feature complete only after end-to-end verification confirms it works, not when the code is written." — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents); [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Verifier quality is the ceiling: "it's important that the task verifier is nearly perfect, otherwise Claude will solve the wrong problem." — [Anthropic Engineering](https://www.anthropic.com/engineering/building-c-compiler)
- Self-grading is untrustworthy: agents "respond by confidently praising the work—even when ... obviously mediocre"; single-context failure modes are "agentic laziness", "self-preferential bias", "goal drift". — [mirror of 2026-03-24 post](https://github.com/celesteanders/harness/blob/main/docs/research/260324_anthropic_harness_design.md); [Claude blog](https://claude.dev/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code/)
- Hooks are the enforcement slot: they "run in your application process, not inside the agent's context window, so they don't consume context" and a `PreToolUse` rejection "prevents it from executing"; `Stop` is for "Validate the result, save session state"; `PreCompact` for archiving; hooks are "the right place for guarantees that must hold in every mode." — [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop); [Permissions](https://platform.claude.com/docs/en/agent-sdk/permissions)
- Rules that must survive compaction belong in CLAUDE.md, "because CLAUDE.md content is re-injected on every request"; keep it under ~200 lines and move workflow detail into on-demand skills. — [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop); [Manage costs](https://code.claude.com/docs/en/costs)
- Prose rules alone are weakly enforced (cited at "4–16%") and the field is migrating "from prompt prose to configuration". — [Marmelab](https://marmelab.com/blog/2026/09/24/the-state-of-ai-harness-engineering-2026.html); [arXiv 2609.00006](https://arxiv.org/abs/2609.00006)
- Evidence attests execution, not replay: the Terminal-Bench / Scaffold Effect work recommends reporting token usage, latency and the complete harness spec alongside any pass/fail. — [arXiv 2607.22585](https://arxiv.org/abs/2607.22585)
- Economics: `/clear` between unrelated tasks; compact only at natural breaks with a warm cache; subagents for verbose verification output; hooks to pre-filter test output ("tens of thousands of tokens to hundreds"). — [Manage costs](https://code.claude.com/docs/en/costs); [Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching)
- Harness components are provisional: Anthropic removed sprints when Opus 4.6 "plans more carefully, sustains agentic tasks for longer", following "only increase complexity when needed." — [mirror of 2026-03-24 post](https://github.com/celesteanders/harness/blob/main/docs/research/260324_anthropic_harness_design.md); [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

### Inferences
- A plugin whose gates are programs invoked by hooks (e.g. a `PreToolUse`/`Stop` hook that refuses a merge until a proof plan is satisfied) sits exactly where Anthropic says machine-held guarantees belong; a gate expressed only as prose in CLAUDE.md or a skill is, per the community evidence, enforced a small fraction of the time.
- The "done" ledger should be a signed/derived machine artifact (JSON or a program's output), never a Markdown checklist the agent can edit, and it should be flipped only by an evaluator with a context separate from the author's — Anthropic's evaluator-role finding and the SDK's fresh-context subagents both support a reviewer that never reads the author's own report.
- Evidence should record what executed (tokens, calls, wall time, harness version), because replayed or cached passes are indistinguishable from real ones otherwise — the same point the benchmark literature makes about harness disclosure.
- Session budgeting rule that follows from Anthropic's economics: one unit of work per session; externalise state (progress file, memory, git) so a fresh session is cheap; run heavy gates once at the end of a batch (each gate run re-bills the whole resident context); prefer `/clear` + re-read of a small ledger over compaction when continuity is not needed.
- Because Anthropic itself prunes harness structure as models improve, the plugin's gates should each carry a stated assumption about what the model cannot yet be trusted to do, so they can be retired deliberately rather than rotting (the "harness rot" problem the Marmelab survey names).

### Gaps
- No Anthropic source prescribes a specific "definition of done" schema beyond the feature-list JSON shape; the plugin's proof-plan format has no first-party template to align to.
- Anthropic has not published guidance on plugin-level hook ordering when several plugins register `Stop`/`PreToolUse` hooks; interaction behaviour would need to be tested, not cited.
