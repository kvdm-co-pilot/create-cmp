## KQ1 — The Claude Code best-practices guide (Apr 2025) and its 2026 revisions

### Takeaway
The April-2025 blog post has been folded into a living docs page whose first and longest section is now "Give Claude a way to verify its work", ahead of explore→plan→code→commit; the 2026 revision adds a four-rung verification ladder (prompt → `/goal` → Stop hook → second-opinion subagent/workflow), a "let Claude interview you → SPEC.md → fresh session" spec step, an explicit "adversarial review step", auto mode as the default permission mode (v2.1.283), and a caveat that plan mode is overhead for one-sentence diffs. The 2025 patterns (TDD, visual iteration, /clear, course-correct early, headless fan-out, writer/reviewer split, worktrees) all survive, reworded.

### Cited Findings
- The guide now opens by naming the governing constraint: "Most best practices are based on one constraint: Claude's context window fills up fast, and performance degrades as it fills." — [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)
- Verification is the first substantive section: "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available, and you become the verification loop… Give Claude something that produces a pass or fail, and the loop closes on its own." — [Best practices](https://code.claude.com/docs/en/best-practices)
- The check "is anything that returns a signal Claude can read in the conversation: a test suite, a build exit code, a linter, a script that diffs output against a fixture, or a browser screenshot compared against a design." A new `/verify` skill is recommended to run yourself "after Claude's check passes to confirm the change against the running app." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Four rungs for "how hard it gates the stop": (1) in one prompt; (2) across a session as a `/goal` condition re-checked by a separate evaluator after every turn; (3) "As a deterministic gate: a Stop hook runs your check as a script and blocks the turn from ending until it passes"; (4) "By a second opinion: a verification subagent or a dynamic workflow that checks its own findings has a fresh model try to refute the result, so the agent doing the work isn't the one grading it." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Evidence over assertion: "Have Claude show evidence rather than asserting success: the test output, the command it ran and what it returned, or a screenshot of the result. Reviewing evidence is faster than re-running the verification yourself, and it works for sessions you weren't watching." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Explore → Plan → Implement → Commit is retained as "the recommended workflow" with plan mode (`Shift+Tab` / `claude --permission-mode plan`) and `Ctrl+G` to edit the plan in an editor; new 2026 caveat: "Plan mode is useful, but also adds overhead… If you could describe the diff in one sentence, skip the plan." — [Best practices](https://code.claude.com/docs/en/best-practices)
- 2025 prompting tips carried forward as before/after tables: scope the task, point to sources (git history), reference existing patterns, describe the symptom + "write a failing test that reproduces the issue, then fix it"; rich content via `@` files, pasted images, URLs, `cat error.log | claude`. — [Best practices](https://code.claude.com/docs/en/best-practices)
- CLAUDE.md guidance: "For each line, ask: 'Would removing this cause Claude to make mistakes?' If not, cut it. Bloated CLAUDE.md files cause Claude to ignore your actual instructions!"; include "Repository etiquette (branch naming, PR conventions)"; `/doctor` proposes cuts; move sometimes-relevant knowledge to skills. — [Best practices](https://code.claude.com/docs/en/best-practices)
- Hooks vs CLAUDE.md: "Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens." Failure-pattern fix: "If Claude already does something correctly without the instruction, delete it or convert it to a hook." — [Best practices](https://code.claude.com/docs/en/best-practices)
- New spec step: "for larger features have Claude interview you and write a spec before you start implementing" using the `AskUserQuestion` tool; "Once the spec is complete, start a fresh session to execute it… The most useful specs are self-contained: they name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step that proves the feature works. Time spent making the spec precise pays off more than time spent watching the implementation." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Course-correct early (2025, reaffirmed): `Esc`, `Esc Esc`/`/rewind`, "Undo that", `/clear`; "If you've corrected Claude more than twice on the same issue in one session… Run `/clear` and start fresh with a more specific prompt." Rewind/checkpoints are new since 2025 (auto file snapshots before each change; "This isn't a replacement for git"). — [Best practices](https://code.claude.com/docs/en/best-practices)
- Headless (2025, reaffirmed): `claude -p` "is how you integrate Claude into CI pipelines, pre-commit hooks, or any automated workflow"; fan-out loop over `claude -p … --allowedTools "Edit,Bash(git commit *)"`; new `/batch <instruction>` splits a change "across 5 to 30 subagents. Each subagent works in its own worktree." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Multi-Claude (2025, expanded 2026): six parallel options — worktrees, cross-session messaging, desktop app, cloud, agent view (`claude agents`, research preview), agent teams ("experimental and disabled by default"). Writer/Reviewer table retained: "A fresh context improves code review since Claude won't be biased toward code it just wrote… have one Claude write tests, then another write code to pass them." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Auto mode: "With Claude Code v2.1.283 or later, auto mode is the built-in starting permission mode for interactive terminal and VS Code sessions: a separate classifier model reviews most actions instead of you and blocks only what looks risky." Unattended: `claude --permission-mode auto -p "fix all lint errors"`. — [Best practices](https://code.claude.com/docs/en/best-practices)
- Adversarial review step: "The longer Claude works unattended, the more an independent check matters… A reviewer running in a fresh subagent context sees only the diff and the criteria you give it, not the reasoning that produced the change." Bundled `/code-review` reviews the diff "in a fresh subagent". Warning: "A reviewer prompted to find gaps will usually report some, even when the work is sound… Tell the reviewer to flag only gaps that affect correctness or the stated requirements, and treat the rest as optional." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Named failure patterns include "The trust-then-verify gap… Fix: Always provide verification (tests, scripts, screenshots). If you can't verify it, don't ship it." — [Best practices](https://code.claude.com/docs/en/best-practices)
- The original blog post was published April 18, 2025 at `anthropic.com/engineering/claude-code-best-practices`; that URL now returns 308 → `code.claude.com/docs/en/best-practices` (observed 2026-09-27). — [redirect target](https://code.claude.com/docs/en/best-practices)
- Common-workflows page (companion) adds: `claude --worktree feature-auth` for isolated parallel sessions; `claude --from-pr 1234` to reopen the session linked to a PR; "Do refactoring in small, testable increments"; for scheduled prompts "be explicit about what success looks like and what to do with results. The task runs autonomously, so it can't ask clarifying questions." — [Common workflows](https://code.claude.com/docs/en/common-workflows)

### Inferences
- The re-ordering (verification first, planning second) signals Anthropic's 2026 priority: closing the loop matters more than the shape of the loop. "If you can't verify it, don't ship it" is now stated as a rule, not a tip.
- The 2025 "safe YOLO" (`--dangerously-skip-permissions` in a container) has been effectively superseded by auto mode + sandboxing; the guide no longer leads with the flag.
- The guide treats the human-written spec as an artifact to *execute from a fresh context* — i.e. spec and implementation are separated by a context boundary, which is the same move Anthropic's long-running-agent harnesses make (KQ5).

### Gaps
- The docs page carries no visible "last updated" date; I could not date individual 2026 edits other than by the version numbers they cite (v2.1.283, v2.1.223 etc.).
- I found no Anthropic changelog of *what changed in the guide itself* between Apr 2025 and now; the comparison above is by reading both.

## KQ3 — Plan mode, "grill me" interrogation, spec/PRD-driven agent work

### Takeaway
Anthropic's 2026 position is two-sided: plan first when the approach is uncertain, multi-file, or unfamiliar ("If you could describe the diff in one sentence, skip the plan"), and for larger features have Claude interview you into a self-contained SPEC.md that ends in an end-to-end verification step, then execute in a fresh session. Anthropic's evidence for planning is mostly its harness research (planner→spec→generator→evaluator outperforms single-agent runs; "sprint contracts" agreeing what done means before code) rather than controlled studies; the industry literature (Böckeler, Thoughtworks) endorses spec→plan→implement but warns that "nothing checks that the code matches" the spec.

### Cited Findings
- Plan mode: "Claude reads files and proposes a plan but makes no edits until you approve"; `claude --permission-mode plan` or `Shift+Tab` until `⏸ plan mode on`. — [Common workflows](https://code.claude.com/docs/en/common-workflows). v2.1.280 added a `/plan` command "to switch to plan mode, send initial planning prompt, or display session plan". — [Claude Code CHANGELOG](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md)
- When to plan: "Planning is most useful when you're uncertain about the approach, when the change modifies multiple files, or when you're unfamiliar with the code being modified." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Interview-to-spec prompt (verbatim template): "I want to build [brief description]. Interview me in detail using the AskUserQuestion tool. Ask about technical implementation, UI/UX, edge cases, concerns, and tradeoffs. Don't ask obvious questions, dig into the hard parts I might not have considered. Keep interviewing until we've covered everything, then write a complete spec to SPEC.md." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Plan-against-diff review: "Use a subagent to review the rate limiter diff against PLAN.md. Check that every requirement is implemented, the listed edge cases have tests, and nothing outside the task's scope changed. Report gaps, not style preferences." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Agent teams: "A teammate that Claude spawns while the lead is in plan mode works in read-only plan mode until its plan is ready… Claude Code approves the plan in the lead's session as soon as the request arrives, without the lead reviewing it." — [Agent teams](https://code.claude.com/docs/en/agent-teams)
- Harness evidence (Nov 26, 2025): failure modes are "agents attempting to complete tasks in one session (exhausting context mid-implementation) and prematurely declaring projects complete after partial progress"; the fix is an initializer agent that writes a 200+ item feature list JSON (each `passes: false` initially) plus `claude-progress.txt`, and a coding agent that does one feature per session. "It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality." — [Effective harnesses for long-running agents](https://anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Harness evidence (Mar 24, 2026): planner agent "Expands brief prompts into detailed product specifications"; generator implements and self-evaluates; evaluator "Tests running applications via Playwright MCP" and "Grades against explicit criteria with hard thresholds"; v1 used "sprint contracts" — "agreeing on what 'done' looked like for that chunk of work before any code was written"; the multi-agent design outperformed single-agent "by orders of magnitude in output quality" (Anthropic's own evaluation). — [Harness design for long-running application development](https://anthropic.com/engineering/harness-design-long-running-apps)
- Same post: the earlier context-reset/sprint decomposition was dropped for Opus 4.6's longer context — "Every component in a harness encodes an assumption about what the model can't do on its own, and those assumptions are worth stress testing, both because they may be incorrect, and because they can quickly go stale as models improve." — [Harness design](https://anthropic.com/engineering/harness-design-long-running-apps)
- Managed Agents "Outcomes" (public beta, May 6, 2026) — "defining success criteria for agent iteration". — [Simon Willison live blog](https://simonwillison.net/2026/May/6/code-w-claude-2026/)
- Industry: Böckeler (Oct 15, 2025) distinguishes spec-first, spec-anchored, spec-as-source; Kiro (Requirements→Design→Tasks) "proved overly elaborate for small fixes"; Spec Kit has a "constitution" then Specify→Plan→Tasks and "generates numerous markdown files requiring extensive review"; only Tessl pursues spec-as-source; "Agents frequently ignore instructions or misinterpret existing code"; the term risks becoming "semantically diffused" (spec ≈ detailed prompt). — [Understanding Spec-Driven Development](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html). Search-result summary of the same article: "in all three tools, 'spec' means a Markdown document the agent is supposed to read, but nothing checks that the code matches it" — [Lobsters discussion (secondary)](https://lobste.rs/s/eets29/understanding_spec_driven_development)
- Thoughtworks Radar blip "Spec-driven development" (Nov 2025 edition, ring Assess): "workflows that begin with a structured functional specification, then proceed through multiple steps to break it down into smaller pieces, solutions and tasks"; concerns — "Workflows remain elaborate and opinionated", tools generate "lengthy spec files that are hard to review", "Handcrafting detailed rules for AI ultimately doesn't scale". The page shows the blip as "Not on current edition". — [Thoughtworks Radar: Spec-driven development](https://www.thoughtworks.com/en-us/radar/techniques/spec-driven-development)
- GitHub Spec Kit (Sept 2, 2025): "a small amount of upfront work to create a spec and a plan ensures the AI builds what you actually intend"; `/analyze` "acting as a quality gate"; works with Claude Code, Copilot, Gemini CLI. — [GitHub Blog: Spec-driven development with AI](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)

### Inferences
- Anthropic recommends planning by *cost of being wrong*, not by ceremony: a written spec is justified when execution will be unattended or multi-file; the same guide tells you to skip it for one-sentence diffs. This maps directly onto a lane model (direct vs brief lane).
- The strongest Anthropic evidence that planning helps is indirect: harness experiments where "done" was contracted before code and graded by a separate evaluator beat single-agent runs. The mechanism credited is separation of grading from doing, not the plan document per se.
- Böckeler's critique ("nothing checks the code matches") is the gap Anthropic's `/goal`, Stop hooks and PLAN.md-review subagent are meant to fill — a spec is only load-bearing if something executes it.

### Gaps
- No controlled A/B study from Anthropic quantifying plan-mode vs no-plan outcomes on SWE tasks was found; the "orders of magnitude" claim is Anthropic's internal harness evaluation with no public methodology I could read.
- Thoughtworks' Nov-2025 page labels its own volume ambiguously (the fetched page said "Vol. 34" for Nov 2025 while the Apr-2026 press release is Vol 34); I treat it as the Nov 2025 edition.

## KQ4 — Review and merge: AI review products, humans in the loop, PR conventions, trunk-based flows

### Takeaway
Anthropic now ships three review tiers — local `/code-review` (effort-scaled, fresh subagent), `/code-review ultra` / `claude ultrareview` (cloud multi-agent fleet with independently reproduced findings, ~$5–25/run, "pre-merge confidence on substantial changes"), and managed Code Review on GitHub (Team/Enterprise, ~$15–25/PR, findings "don't approve or block your PR", neutral check run you may gate on yourself) — plus the GitHub Action for custom automation. Guidance consistently keeps a human as final approver, requires posting to be an explicit per-run human choice, and lets repos pin PR/commit attribution via the `attribution` setting (default trailer "Co-Authored-By: Claude …" and footer "🤖 Generated with Claude Code").

### Cited Findings
- `/code-review`: "reviews your branch's commits ahead of its upstream plus any uncommitted changes"; targets a path, PR number, branch or `main...my-feature`; flags `--fix`, `--comment`, `--post`; "runs as a background subagent with its own context window"; effort `low`/`medium` "reports only the findings it's most confident in", `high`–`max` "broaden coverage"; `/review` is an alias since v2.1.223; the command was `/simplify` before v2.1.147. — [Code Review](https://code.claude.com/docs/en/code-review)
- Ultrareview: "research preview"; "Claude Code launches a fleet of reviewer agents in a cloud sandbox"; "every reported finding is independently reproduced and verified"; 5–10 minutes; "The command runs only when you invoke it with `/code-review ultra`; Claude doesn't start an ultrareview on its own"; branch limit 500 files / 8,000 lines by default; Pro/Max 3 free runs then "$5 to $25 in usage credits"; not on Bedrock/Vertex/Foundry or ZDR orgs. — [Find bugs with ultrareview](https://code.claude.com/docs/en/ultrareview)
- Ultrareview posting: "Claude Code never posts unless you choose to on that run, and `--no-post` is the default"; the comment "isn't a review or an approval, and it ends with a 'Generated by Claude Code' note"; CI use via `claude ultrareview [PR|base]` which "blocks until the remote review finishes, and prints the findings to stdout", exit 0/1/130, `--json` emits `bugs.json`, `--timeout` default 45 min. Positioning table: `/code-review` "quick feedback while iterating" vs ultra "pre-merge confidence on substantial changes". — [Ultrareview](https://code.claude.com/docs/en/ultrareview)
- Managed Code Review: "research preview, available for Team and Enterprise"; "multiple agents analyze the diff and surrounding code in parallel… Each agent looks for a different class of issue, then a verification step checks candidates against actual code behavior to filter out false positives"; severities 🔴 Important / 🟡 Nit / 🟣 Pre-existing; "Findings are tagged by severity and don't approve or block your PR"; average 20 minutes; "$15-25" per review; triggers once / every push / manual (`@claude review`, `@claude review always`; behaviour changed July 2026). — [Code Review](https://code.claude.com/docs/en/code-review)
- Gating is left to the repo: "The check run always completes with a neutral conclusion so it never blocks merging… If you want to gate merges on Code Review findings, read the severity breakdown from the check run output in your own CI" (a `gh api … --jq` recipe parses `bughunter-severity: {"normal":2,"nit":1,"pre_existing":0}`). — [Code Review](https://code.claude.com/docs/en/code-review)
- `REVIEW.md` tunables include a "Verification bar: require evidence before a class of finding is posted. For example, 'behavior claims need a `file:line` citation in the source, not an inference from naming'"; "Re-review convergence… after the first review, suppress new nits and post Important findings only"; CLAUDE.md violations are flagged as nits and "if your PR changes code in a way that makes a CLAUDE.md statement outdated, Claude flags that the docs need updating too." — [Code Review](https://code.claude.com/docs/en/code-review)
- GitHub Action (`anthropics/claude-code-action@v1`): interactive mode on `@claude`, automation mode when a `prompt` is given; can run a plugin skill — `plugins: "code-review@claude-code-plugins"` + `prompt: "/code-review:code-review --comment …"`; triggering actor must have write access and be human unless in `allowed_bots`; best practices: "Grant the workflow only the permissions it needs, and review Claude's changes before merging", `--max-turns`, workflow timeouts, concurrency controls; upgrade from `@beta` to `@v1`. — [Claude Code GitHub Actions](https://code.claude.com/docs/en/github-actions)
- Security review layer: `/security-review` "looks for places where potential attacker-controllable input enters"; the Claude Security plugin (beta, Jul 22, 2026) runs inventory → threat model → research → sweep → panel → adversarial; "A candidate finding does not go into the report because a researcher found it. It goes in only after surviving a panel" (2-of-3 quorum; unanimous = high confidence); requires paid plan, v2.1.154+, dynamic workflows enabled. — [MarkTechPost on the Claude Security plugin (secondary)](https://www.marktechpost.com/2026/07/22/anthropic-releases-claude-security-plugin-for-claude-code-in-beta-a-multi-agent-vulnerability-scanner-that-runs-in-your-terminal/); pre-generation guidance and `/security-review` also described in [How Anthropic secures its AI-native SDLC](https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle)
- Attribution: the `attribution` setting (v2.0.62) "replaces and deprecates the previous includeCoAuthoredBy setting"; keys `commit` (trailer) and `pr` (footer), empty string disables; defaults are a `Co-Authored-By: Claude … <noreply@anthropic.com>` trailer and a "🤖 Generated with Claude Code" PR footer. — [ClaudeLog: Attribution setting (secondary)](https://claudelog.com/faqs/attribution-setting-claude-code/); a reported edge case where `attribution.commit: ""` did not disable the trailer — [anthropics/claude-code issue #45137](https://github.com/anthropics/claude-code/issues/45137)

## KQ5 — Verification as a first-class stage: self-verification, "definition of done", evidence/attestation

### Takeaway
Anthropic's 2026 material treats verification as the stage that decides whether unattended work is acceptable: give the agent a pass/fail check, escalate from prompt to `/goal` (fresh Haiku evaluator each turn) to a deterministic Stop hook to a refuting second agent, and require evidence (test output, command + result, screenshot) rather than a claim. For attestation of agent work Anthropic's own practice is logging every approval "with the signals and reasoning behind it" into a SIEM and risk-weighted human sampling; no Anthropic spec for a portable evidence/receipt format was found.

### Cited Findings
- `/goal`: "After each turn, a small fast model checks whether the condition holds"; it "is a wrapper around a session-scoped prompt-based Stop hook"; verdicts Not yet met / Met / Impossible; "completion is decided by a fresh model rather than the one doing the work"; "The evaluator… doesn't run commands or read files independently, so write the condition as something Claude's own output can demonstrate"; a good condition has "One measurable end state… A stated check… Constraints that matter"; stall rule: "If Claude keeps answering the evaluator without making progress (no tool use for several turns in a row), Claude Code stops the loop"; works headless: `claude -p "/goal CHANGELOG.md has an entry for every PR merged this week"`. — [Keep Claude working toward a goal](https://code.claude.com/docs/en/goal)
- Stop hooks as deterministic gates and their cap on consecutive blocks; `TaskCompleted` hook "Exit with code 2 to prevent completion and send feedback", `TeammateIdle` to keep a teammate working — [Agent teams: Enforce quality gates with hooks](https://code.claude.com/docs/en/agent-teams); ladder and "show evidence" rule — [Best practices](https://code.claude.com/docs/en/best-practices)
- Workflows as verifiers: "it can have independent agents adversarially review each other's findings before they're reported"; `/deep-research` returns "a cited report with claims that didn't survive cross-checking filtered out… When the verifier agents can't check a claim… the report lists that claim as unverified instead of counting it as refuted"; example prompts "keep fixing the reported errors until the type check passes or two rounds in a row make no progress" and "adversarially verify each finding before reporting it". — [Dynamic workflows](https://code.claude.com/docs/en/workflows)
- Definition of done in harnesses: feature list with `passes` booleans as ground truth; leave code "in a clean state at the end of a session…the kind of code that would be appropriate for merging to a main branch"; sessions "begin… by verifying basic functionality before implementing new features"; end-to-end checks through Puppeteer MCP. — [Effective harnesses](https://anthropic.com/engineering/effective-harnesses-for-long-running-agents). Evaluator "Grades against explicit criteria with hard thresholds" and "Requires prompt tuning to avoid over-leniency toward AI outputs". — [Harness design](https://anthropic.com/engineering/harness-design-long-running-apps)
- Anthropic's own attestation practice: "Every approval is logged with the signals and reasoning behind it"; decisions "land in the SIEM for post-hoc attribution"; "Review risk-weighted sampling of automated approvals"; the audit trail is used "to validate decisions retroactively rather than gate every action upfront". — [How Anthropic secures its AI-native SDLC](https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle)
- Migration loop: "reviewers cite the rule behind every finding" so "drift has nowhere to hide"; "100% of existing test suite passed in CI before merge". — [AI code migration](https://claude.com/blog/ai-code-migration)
- Headless evidence hooks for CI: `--output-format json` includes `total_cost_usd`; `system/init` carries `plugin_errors` and `mcp_server_errors` "so a CI gate can fail on a non-empty array"; `--bare` "is the recommended mode for scripted and SDK calls, and will become the default for `-p` in a future release"; `--json-schema` structured output; `--permission-prompts none` for unattended runs. — [Run Claude Code programmatically](https://code.claude.com/docs/en/headless)
- Review evidence standard: `REVIEW.md` "Verification bar" ("behavior claims need a `file:line` citation"); findings carry "a collapsible extended reasoning section… how it verified the problem". — [Code Review](https://code.claude.com/docs/en/code-review)
- Course framing: "Verify unsupervised runs in proportion to how little you watched them". — [Class Central listing of Claude Code in Action](https://www.classcentral.com/course/anthropic-academy-claude-code-in-action-536160)
- Industry: Thoughtworks Radar Vol 34 (Apr 15, 2026) themes "Putting coding agents on a leash" and "Securing permission-hungry agents"; control mechanisms split into "feedforward approaches (Agent Skills, spec-driven development) and feedback strategies like mutation testing to enable self-correction before human review"; risk of "cognitive debt" as the gap between human comprehension and system complexity widens; "The inflection point we're at isn't so much about technology — it's about technique." (Rachel Laycock, CTO). — [Thoughtworks news: Radar Vol 34](https://www.thoughtworks.com/about-us/news/2026/combat-ai-cognitive-debt-radar-v34)
- Industry: Kief Morris (Mar 4, 2026) — humans should be "on the loop": "The right place for us humans is to build and manage the working loop rather than either leaving the agents to it or micromanaging what they produce"; in-the-loop review of every artifact "Creates bottlenecks since agents generate code faster than humans review it". — [Humans and Agents in Software Engineering Loops](https://martinfowler.com/articles/exploring-gen-ai/humans-and-agents.html)

### Inferences
- Anthropic's DoD for an agent is operational, not documentary: a condition an evaluator can check from the transcript, or a script a Stop hook can run. "Done" is whatever the gate accepts.
- The recurring pattern across `/goal`, ultrareview, Code Review, the Security plugin and `/deep-research` is *refutation by a fresh model*: Anthropic distrusts self-grading and instruments a second agent to try to knock the result down.
- Anthropic attests agent work by logging *reasons and signals* alongside approvals, then sampling — a receipts-style model, but internal and SIEM-bound rather than a shipped artifact format.

### Gaps
- No Anthropic document defines a portable "evidence receipt" or attestation schema for agent output (nothing like in-toto/SLSA for agents was found under Anthropic's name).
- The `/verify` skill referenced by the best-practices guide was not fetched; its exact behaviour (what it runs, what it records) is unverified here.

## KQ6 — Multi-agent SDLC: subagents, agent teams, dynamic workflows/ultracode, cloud sessions, routines — when Anthropic recommends each, and pitfalls

### Takeaway
Anthropic's 2026 docs give a clear decision rule — subagents when only the result matters (cheapest), agent teams when peers must debate (experimental, off by default, tokens scale linearly, prefer 3–5 teammates and research/review tasks first), dynamic workflows when the orchestration itself should be a rerunnable script (dozens–hundreds of agents, resumable, but no mid-run human input), routines/cloud sessions when work must run without a laptop (cron, API, GitHub webhook). Named pitfalls: teammates stopping early or lead stopping before tasks complete, task-status lag, no session resume for in-process teammates, cost warnings at 25 agents / 1.5M tokens, and the classifier treating inter-agent "approval" messages as untrusted.

### Cited Findings
- Decision table: "Who decides what runs next — Subagents: Claude, turn by turn; Skills: Claude, following the prompt; Agent teams: The lead agent, turn by turn; Workflows: The script." Scale: subagents "A few delegated tasks per turn", teams "A handful of long-running peers", workflows "Dozens to hundreds of agents per run". Interruption: teams "Teammates keep running", workflows "Resumable in the same session". — [Dynamic workflows](https://code.claude.com/docs/en/workflows)
- Subagents vs teams: "Use subagents when you need quick, focused workers that report back. Use agent teams when teammates need to share findings, challenge each other, and coordinate on their own." Token cost: subagents "Lower: results summarized back", teams "Higher: each teammate is a separate Claude instance". — [Agent teams](https://code.claude.com/docs/en/agent-teams)
- Agent teams status and use cases: "experimental and disabled by default" (`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`); strongest for "Research and review", "New modules or features", "Debugging with competing hypotheses", "Cross-layer coordination"; "For sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective"; "Start with 3-5 teammates"; "Three focused teammates often outperform five scattered ones"; "Start with research and review… without the coordination challenges that come with parallel implementation"; not available under `-p`/Agent SDK. — [Agent teams](https://code.claude.com/docs/en/agent-teams). Secondary: introduced as research preview in v2.1.32 on 2026-02-05 — [Promptessor (secondary)](https://promptessor.com/blog/claude-code-agent-teams-examples-and-multi-agent-workflows-for-parallel-development-in-2026)
- Agent-team pitfalls (verbatim headings): "Teammates not appearing", "Claude spawns teammates instead of subagents" (a *named* subagent launches as a teammate while teams are on), "Too many permission prompts" (bubble to the lead), "Agents stopping early… The lead can stop early too, deciding the team is finished before all tasks are actually complete", "Orphaned tmux sessions"; limitations: "No session resumption with in-process teammates", "Task status can lag", "One team per session", "No nested teams", "Lead is fixed"; safety: "A teammate can't approve a permission prompt or supply consent on your behalf" and the auto-mode classifier "treats an approval claim relayed from another agent as untrusted input". — [Agent teams](https://code.claude.com/docs/en/agent-teams)
- Dynamic workflows (blog May 28, 2026): Claude "dynamically writes orchestration scripts"; `ultracode` = `xhigh` effort + automatic workflow planning; suited to "codebase-wide audits, large migrations, and critical work requiring independent verification"; "consume substantially more tokens than a typical Claude Code session". — [Introducing dynamic workflows in Claude Code](https://claude.com/blog/introducing-dynamic-workflows-in-claude-code); InfoQ (Jun 1, 2026): "Anthropic recommends starting with smaller, well-scoped tasks before scaling" — [InfoQ](https://www.infoq.com/news/2026/06/dynamic-workflows-claude-code/)
- Workflow mechanics and limits: script API `agent()`, `pipeline()`, `parallel()`, `phase()`, `log()`, `args`, `schema`; "No mid-run user input… For sign-off between stages, run each stage as its own workflow"; "No direct filesystem or shell access from the workflow itself"; `Date.now()`/`Math.random()` throw "so that a relaunched run repeats the same `agent()` calls"; 16 concurrent agents default, 1,000 agents/run, 4,096 items per `parallel()`/`pipeline()`; `Large workflow` warning at >25 agents or >1.5M projected tokens; size guideline small/medium/large; saved scripts live in `.claude/workflows/` and can be shipped in a plugin's `workflows/` dir, namespaced `/plugin:name`; `/workflow-authoring` skill (v2.1.248+); the `ultracode` keyword is ignored when it "reaches the session another way: a prompt passed with `-p`… a webhook payload or pull request comment" (since v2.1.210, a prompt-injection guard). — [Dynamic workflows](https://code.claude.com/docs/en/workflows)
- Worktrees: `claude --worktree <name>` → `.claude/worktrees/<name>/` on branch `worktree-<name>`; subagents can be isolated with `isolation: worktree` frontmatter; unchanged subagent worktrees are removed automatically and a periodic sweep removes older ones; Claude Code blocks edits/commands that reach the main checkout from an isolated worktree; `--worktree "#1234"` branches from a PR; `.worktreeinclude` copies gitignored env files. — [Worktrees](https://code.claude.com/docs/en/worktrees)
- Routines (Apr 14, 2026): "configured once with a prompt, repository, and connectors, then executed on a schedule, via API call, or triggered by events"; use cases "Backlog triage… Documentation drift detection… Deploy verification and smoke testing… Alert triage with proposed fixes… Custom code review checklists"; limits Pro 5/day, Max 15/day, Team/Enterprise 25/day. — [Introducing routines in Claude Code](https://claude.com/blog/introducing-routines-in-claude-code). Scheduling comparison table (Routines / desktop scheduled tasks / GitHub Actions / `/loop`). — [Common workflows](https://code.claude.com/docs/en/common-workflows)
- Cloud/cost pitfalls: teams "use significantly more tokens than a single session… For routine tasks, a single session is more cost-effective"; subagent/teammate prompt cache TTL is 5 minutes by default (`subagentPromptCacheTtl: 1h` to extend, billed higher). — [Agent teams](https://code.claude.com/docs/en/agent-teams); workflow fan-outs stagger sibling agents up to 5 s to share the cached prefix. — [Dynamic workflows](https://code.claude.com/docs/en/workflows)
- Headless multi-agent: `claude -p` "stays open until [a background subagent or workflow] completes… By default the wait ends after 10 minutes of continuous idle waiting". — [Run Claude Code programmatically](https://code.claude.com/docs/en/headless)
- Code with Claude (May 6, 2026) framing: "infrastructure, rather than intelligence, is now the bottleneck for production agents"; multi-model advice "a smaller executor model, such as Haiku, calls a larger advisor model, such as Opus, only on the hard cases"; Managed Agents multi-agent orchestration (public beta). — [InfoQ: Code with Claude](https://www.infoq.com/news/2026/05/code-with-claude/)

### Inferences
- Anthropic's ordering is by *who holds the plan*: keep it in the model for small work, move it to a script when repeatability and scale matter. For an enforced delivery loop, that argues for workflows (deterministic control flow, resumable, auditable script) over agent teams (emergent coordination, experimental).
- Workflows' "no mid-run input" plus "run each stage as its own workflow" is Anthropic's own answer to human sign-off points: stage boundaries are where humans belong.
- Several 2026 guards (keyword ignored from webhooks; approval claims between agents untrusted; teammates cannot consent) show Anthropic hardening multi-agent surfaces against prompt injection through the coordination channel itself.

### Gaps
- Availability statements for dynamic workflows conflict: the docs say "available on all paid plans" (Pro via `/config`), the May-28 blog says GA for Pro/Max/Team/Enterprise, InfoQ (Jun 1) called it a research preview on Max/Team/Enterprise. Treat the docs as current.
- I did not fetch the sub-agents or cross-session-messaging pages; details on concurrent subagent limits and messaging semantics come only from cross-references.

## KQ7 — Industry framing: Thoughtworks/Fowler, GitHub, Microsoft, Google vs Anthropic (short comparison)

### Takeaway
Everyone converges on spec → plan → implement → verify with a human "on the loop"; the divergence is *what enforces the spec*. Thoughtworks/Böckeler warn that markdown specs are unverified and verbose (Assess, not Trial); GitHub/Microsoft ship spec pipelines with a validator stage and optional human gate; Google positions Jules as queue-and-PR asynchronous delegation; Anthropic is distinctive in pushing enforcement into runtime mechanisms (Stop hooks, `/goal`, refuting agents, neutral-but-parseable review checks) and in publishing its own internal SDLC numbers.

### Cited Findings
- Thoughtworks Radar Vol 34 (Apr 15, 2026) themes: "Retaining principles, relinquishing patterns", "Securing permission-hungry agents", "Putting coding agents on a leash", "Evaluating technology in an agentic world"; fundamentals (zero trust, DORA metrics, testability) "remain essential". — [Thoughtworks news release](https://www.thoughtworks.com/about-us/news/2026/combat-ai-cognitive-debt-radar-v34); SDD blip (Nov 2025, Assess) — [Radar: Spec-driven development](https://www.thoughtworks.com/en-us/radar/techniques/spec-driven-development)
- Böckeler: SDD ladder spec-first / spec-anchored / spec-as-source; parallels to failed Model-Driven Development; review burden of verbose markdown. — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html). Morris: humans "on the loop", engineering "the harness — specifications, quality checks, and workflow guidance". — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/humans-and-agents.html)
- GitHub Spec Kit (Sept 2, 2025): constitution → `/specify` → `/plan` → `/tasks`, `/analyze` as a quality gate; agent-agnostic (Copilot, Claude Code, Gemini CLI). — [GitHub Blog](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)
- Microsoft `agentic-sdlc-starter` defines agentic SDLC as "PRD + User Stories → Production-Ready Code" via Assessor → Resolver → Specifier → Generator → Validator; "The Generator reads only the specs and copilot-instructions — it never sees the PRD or TDD directly"; the Resolution Gate "can be automated (agent resolves from docs), human-gated (PR review), or hybrid." — [microsoft/agentic-sdlc-starter](https://github.com/microsoft/agentic-sdlc-starter)
- Google Jules: asynchronous agent that clones the repo into a Cloud VM; "built around queueing rather than live chat—you describe a task, walk away, and a pull request arrives later"; Gemini CLI extension for delegation. — [Google blog: Jules](https://blog.google/innovation-and-ai/models-and-research/google-labs/jules/); [Google Developers Blog](https://developers.googleblog.com/jules-gemini-3/)
- Adoption context (secondary): Copilot 29% global workplace adoption Jan 2026 vs Claude Code 18% (24% US/Canada). — [Codewave (secondary)](https://codewave.com/feeds/blog/latest-updates-trends-coding-agents-sdlc-automation-ai-2026)

### Inferences
- Convergence: all four camps separate intent from implementation and insert a validator; all keep a human gate somewhere. Contradiction: Thoughtworks' "Assess" and Böckeler's MDD warning cut against GitHub's/Microsoft's heavy multi-document pipelines; Anthropic sidesteps by keeping the spec short (SPEC.md ending in a verification step) and putting weight on runtime gates rather than document volume.
- Anthropic and Microsoft agree on context isolation (Anthropic: execute the spec in a fresh session; Microsoft: Generator sees only the specs).

### Gaps
- I did not fetch Google's or GitHub's 2026 *guidance* documents on agentic SDLC (only product pages); the comparison there rests on positioning rather than published practice.
- Thoughtworks Radar Vol 34 blip-level text (e.g., "AI-friendly code design", mutation testing ring) was not read; only the press release.

## Implications for a Claude Code plugin repo (create-cmp: brief → build → prove → review → merge with evidence receipts)

### Takeaway
Anthropic's 2026 guidance describes, almost rung for rung, the loop create-cmp enforces — and the places where Anthropic's own tooling now offers primitives the plugin can adopt or interoperate with (Stop/TaskCompleted hooks, `/goal`, workflows shipped in plugins, `REVIEW.md` verification bars, machine-readable Code Review severities, headless `plugin_errors` gating, `attribution`). The main cautions are Anthropic's: gates encode assumptions that go stale, reviewers asked for gaps will find them, and multi-agent ceremony costs tokens linearly.

### Cited Findings
- Deterministic gate = the plugin's proof-gate model: "hooks are deterministic and guarantee the action happens"; Stop hook "blocks the turn from ending until it passes"; `TaskCompleted` "Exit with code 2 to prevent completion". — [Best practices](https://code.claude.com/docs/en/best-practices); [Agent teams](https://code.claude.com/docs/en/agent-teams)
- Evidence receipts = "Have Claude show evidence rather than asserting success… it works for sessions you weren't watching"; Anthropic logs "the signals and reasoning behind" every approval and samples them. — [Best practices](https://code.claude.com/docs/en/best-practices); [Secure SDLC](https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle)
- Brief lane vs direct lane = "If you could describe the diff in one sentence, skip the plan" and "for larger features have Claude interview you and write a spec"; specs should "end with an end-to-end verification step that proves the feature works". — [Best practices](https://code.claude.com/docs/en/best-practices)
- Adversarial reviewer landing gaps, capped = "Tell the reviewer to flag only gaps that affect correctness or the stated requirements"; `REVIEW.md` "Re-review convergence… suppress new nits and post Important findings only". — [Best practices](https://code.claude.com/docs/en/best-practices); [Code Review](https://code.claude.com/docs/en/code-review)
- Spec-mirror-drift = "reviewers cite the rule behind every finding" so "drift has nowhere to hide"; Code Review flags a PR that "makes a CLAUDE.md statement outdated". — [AI code migration](https://claude.com/blog/ai-code-migration); [Code Review](https://code.claude.com/docs/en/code-review)
- Gate hygiene = "Every component in a harness encodes an assumption about what the model can't do on its own, and those assumptions are worth stress testing… they can quickly go stale as models improve." — [Harness design](https://anthropic.com/engineering/harness-design-long-running-apps)
- Plugin-shipped orchestration: workflows can live in a plugin's `workflows/` directory and run as `/plugin:name`; scripts are deterministic (no `Date.now()`), resumable, "No mid-run user input… run each stage as its own workflow". — [Dynamic workflows](https://code.claude.com/docs/en/workflows)
- CI: GitHub Action can install a marketplace plugin and run `/plugin:skill` as the prompt; `--bare` recommended for scripts; `plugin_errors`/`mcp_server_errors` in `system/init` let "a CI gate… fail on a non-empty array"; `claude ultrareview --json` exits 0/1 with `bugs.json`; Code Review severity is parseable from the check run. — [GitHub Actions](https://code.claude.com/docs/en/github-actions); [Headless](https://code.claude.com/docs/en/headless); [Ultrareview](https://code.claude.com/docs/en/ultrareview); [Code Review](https://code.claude.com/docs/en/code-review)
- Non-blocking review products: "Findings… don't approve or block your PR"; "The check run always completes with a neutral conclusion". — [Code Review](https://code.claude.com/docs/en/code-review)
- Injection-hardened coordination: `ultracode` ignored from webhook/PR-comment text; inter-agent approval claims untrusted; teammates cannot consent. — [Dynamic workflows](https://code.claude.com/docs/en/workflows); [Agent teams](https://code.claude.com/docs/en/agent-teams)
- Attribution is configurable per repo via `attribution.commit` / `attribution.pr` (v2.0.62). — [ClaudeLog (secondary)](https://claudelog.com/faqs/attribution-setting-claude-code/)
- Cost discipline: teams' tokens "scale linearly"; workflows warn at 25 agents / 1.5M tokens; "Don't use the largest model for everything. Token spend concentrates in your loops". — [Agent teams](https://code.claude.com/docs/en/agent-teams); [Dynamic workflows](https://code.claude.com/docs/en/workflows); [AI code migration](https://claude.com/blog/ai-code-migration)

### Inferences
- create-cmp's thesis ("the agent authors, an existing program refuses") is now Anthropic's stated rung 3 of verification; the differentiator is not the gate but the *portable receipt* — Anthropic's evidence trail is internal (SIEM) and its review products emit findings, not signed attestations of what was executed.
- The plugin should expect its users to run in auto mode by default (v2.1.283) and to invoke it from routines/CI where nobody answers prompts — gates must fail closed with named reasons, as `/goal`, ultrareview and worktree isolation do in Anthropic's own docs.
- Because Anthropic's review checks are neutral by design, a plugin that wants Code Review or ultrareview in its merge gate must read their machine-readable outputs itself — the same "program at the moment of decision" stance the repo already takes.
- Böckeler's objection to SDD ("nothing checks the code matches the spec") is the exact market gap a prove-stage receipt closes; Thoughtworks' Vol-34 "feedforward + feedback" vocabulary is a ready-made way to describe brief (feedforward) and prove/review (feedback) to that audience.

### Gaps
- No Anthropic source addresses plugin-authored hooks *overriding* or composing with user `/goal`/Stop hooks (precedence when both gate the same turn) — worth testing empirically.
- Whether Code Review's `REVIEW.md` is read by `/code-review` local runs is explicitly *no* ("it doesn't read REVIEW.md"); a plugin that wants one rulebook for both must duplicate or generate it. — [Code Review](https://code.claude.com/docs/en/code-review)
