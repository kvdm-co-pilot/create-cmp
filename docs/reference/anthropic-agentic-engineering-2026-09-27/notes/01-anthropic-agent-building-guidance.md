## Key question 1: Anthropic's named agentic patterns and when NOT to use agents

### Takeaway
"Building effective agents" (Dec 19, 2024) defines workflows (predefined code paths) vs agents (LLM directs its own process), names five workflow patterns plus the augmented LLM, and insists on starting with the simplest solution — a stance every later Anthropic publication reaffirms, most sharply in the March 2026 harness post ("every component in a harness encodes an assumption about what the model can't do on its own").

### Cited Findings
- EARLIER GUIDANCE (Dec 19, 2024, Erik Schluntz & Barry Zhang): *Workflows* are "systems where LLMs and tools are orchestrated through predefined code paths"; *agents* are "systems where LLMs dynamically direct their own processes and tool usage" — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- The **augmented LLM** (retrieval, tools, memory) is the basic building block; the model "actively generates search queries, selects tools, and determines information retention" — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- Five named patterns and their when-to-use: **Prompt chaining** for "tasks [that] can be easily and cleanly decomposed into fixed subtasks"; **Routing** for "complex tasks where there are distinct categories that are better handled separately"; **Parallelization** (sectioning and voting) when "multiple perspectives or attempts are needed for higher confidence results"; **Orchestrator-workers** for "complex tasks where you can't predict the subtasks needed" (e.g., multi-file code changes); **Evaluator-optimizer** when there are "clear evaluation criteria" and "iterative refinement provides measurable value" — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- When NOT to use agents: "Agentic systems often trade latency and cost for better task performance"; for many applications "optimizing single LLM calls with retrieval and in-context examples is usually enough"; add complexity only when it demonstrably improves outcomes — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- Three core principles: (1) simplicity, (2) transparency by "explicitly showing the agent's planning steps", (3) "carefully craft your agent-computer interface (ACI) through thorough tool documentation and testing" — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- Reference implementations of these patterns live in the cookbook `patterns/agents` directory: `basic_workflows.ipynb` (chaining, routing, parallelization), `evaluator_optimizer.ipynb`, `orchestrator_workers.ipynb`, plus newer `async_multi_agent_orchestration.ipynb` and `latency_multi_agent.ipynb` (multi-agent teams under latency and budget limits) — [anthropic-cookbook patterns/agents](https://github.com/anthropics/anthropic-cookbook/tree/main/patterns/agents)
- Barry Zhang's talk "How We Build Effective Agents" (AI Engineer Summit, NYC, 2025) framed it as three principles: "do not build agents for everything, keep them simple, and think like the agent"; agents suit "valuable, ambiguous tasks where the system must decide what to do next"; "a model, a clear environment, well-described tools, and a strong system prompt are often enough to begin" — [Class Central listing of the talk](https://www.classcentral.com/course/youtube-how-we-build-effective-agents-barry-zhang-anthropic-457735); secondary write-up with the four-item checklist (complexity, value, de-risk critical capabilities, cost of error & discoverability), "Agents are models using tools in a loop", and "Any complexity upfront is really going to kill iteration speed" — [dev.to summary](https://dev.to/bokuno_log/how-we-build-effective-agents-3-principles-from-anthropics-barry-zhang-gfo). The talk's YouTube ID appears as `D7_ipDqhtwk` in secondary listings — [videohighlight listing](https://videohighlight.com/v/D7_ipDqhtwk?mediaType=youtube&language=en&summaryType=default&aiFormatted=false)
- 2026 REAFFIRMATION: "Find the simplest solution possible, and only increase complexity when needed"; "Every component in a harness encodes an assumption about what the model can't do on its own, and those assumptions are worth stress testing"; re-examine harnesses with each model release — [Harness design for long-running application development (Mar 24, 2026)](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- 2026 REAFFIRMATION (Claude Code docs): "Plan mode is useful, but also adds overhead... If you could describe the diff in one sentence, skip the plan" — [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)
- 2026 REAFFIRMATION (dynamic workflows): "For regular coding tasks, try and ask yourself: does it really need more compute?" — [A harness for every task (Jun 2, 2026)](https://claude.dev/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code/)
- 2026 NUANCE on prompt chaining: "With adaptive thinking and subagent orchestration, Claude handles most multistep reasoning internally. Explicit prompt chaining... is still useful when you need to inspect intermediate outputs or enforce a specific pipeline structure. The most common chaining pattern is self-correction: generate a draft → have Claude review it against criteria → have Claude refine" — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- 2026 model-specific de-scaffolding: for Fable 5, "Skills developed for prior models are often too prescriptive for Claude Fable 5 and can degrade output quality. Review and consider removing older instructions if default performance is better" — [Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)

### Inferences
- The 2024 taxonomy is unchanged and repeatedly reaffirmed; what changed is the *bar* for adding a component — 2026 guidance treats each harness component as a falsifiable hypothesis to be ablated per model release.
- "Deterministic code path where possible, agent where necessary" is the consistent thread: workflows for predictable decomposition, agents for ambiguity.

## Key question 2: Agent-computer interface (ACI) and "Writing effective tools for agents"

### Takeaway
Anthropic's tool rules: fewer, consolidated, namespaced tools; docstring-quality descriptions; "poka-yoke" argument design; token-efficient responses with pagination/truncation and actionable errors; and an eval-then-iterate loop in which Claude itself rewrites tool descriptions. 2025–26 platform features (Tool Search, Programmatic Tool Calling, Tool Use Examples, code execution with MCP) are the productised form of the same rules.

### Cited Findings
- EARLIER GUIDANCE (Dec 2024, Appendix 2 "Prompt engineering your tools"): "Give the model enough tokens to 'think' before it writes itself into a corner"; "Keep the format close to what the model has seen naturally occurring in text"; avoid formatting "overhead" such as "having to keep an accurate count"; write tool definitions "as if writing a great docstring for a junior developer"; "Run many example inputs to see what mistakes the model makes, and iterate"; poka-yoke — "Change the arguments so that it is harder to make mistakes" (the SWE-bench agent switched to absolute file paths) — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- EARLIER GUIDANCE (Sep 11, 2025, Ken Aizawa et al.): "More tools don't always lead to better outcomes"; tools should "consolidate functionality, handling potentially multiple discrete operations (or API calls) under the hood" (e.g., `schedule_event` instead of `list_users` + `create_event`); "Namespacing (grouping related tools under common prefixes) can help delineate boundaries between lots of tools" (`asana_projects_search`); return interpretable names not "cryptic UUIDs"; offer a `response_format` enum (`detailed` / `concise`); implement "pagination, range selection, filtering, and/or truncation with sensible default parameter values"; error messages should give "specific and actionable improvements, rather than opaque error codes"; "think of how you would describe your tool to a new hire"; use unambiguous parameter names (`user_id` not `user`); "Even small refinements to tool descriptions can yield dramatic improvements"; collect metrics: "total runtime of individual tool calls and tasks, the total number of tool calls, the total token consumption, and tool errors"; loop = prototype locally → run real multi-tool evals → have Claude Code analyse transcripts and rewrite tools — [Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)
- EARLIER GUIDANCE (Jun 13, 2025): "Agent-tool interfaces are as critical as human-computer interfaces"; a tool-testing agent that rewrote descriptions "decreased task completion time by 40%" — [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- EARLIER GUIDANCE (Sep 29, 2025): good tools are "self-contained, robust to error, and extremely clear with respect to their intended use"; failure mode is "bloated tool sets that cover too much functionality or lead to ambiguous decision points about which tool to use" — [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- EARLIER GUIDANCE (Mar 20, 2025) "think" tool: a no-op tool letting Claude "stop and think" mid-response, distinct from extended thinking; recommended for tool-output analysis, policy-heavy environments, sequential decisions; τ-bench airline pass^1 0.570 vs 0.370 baseline ("a 54% relative improvement"), retail 0.812 vs 0.783 — [The "think" tool](https://www.anthropic.com/engineering/claude-think-tool)
- EARLIER GUIDANCE (Nov 4, 2025) code execution with MCP: presenting MCP servers as code APIs on a filesystem with progressive disclosure cut one workflow from 150,000 to 2,000 tokens ("a time and cost saving of 98.7%"); benefits: filter results in code, control flow in code, "Intermediate results stay in the execution environment by default"; trade-off: needs "a secure execution environment with appropriate sandboxing, resource limits, and monitoring" — [Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp)
- EARLIER GUIDANCE (Nov 24, 2025) advanced tool use: **Tool Search Tool** ("tool definitions consume 134K tokens before optimization"; 85% token reduction; Opus 4 accuracy 49%→74%, Opus 4.5 79.5%→88.1%; use when definitions exceed ~10K tokens or 10+ MCP tools); **Programmatic Tool Calling** ("When Claude orchestrates 20+ tool calls in a single code block, you eliminate 19+ inference passes"; 37% token reduction 43,588→27,297); **Tool Use Examples** ("JSON Schema excels at defining structure… but it can't express usage patterns"; accuracy 72%→90% on complex parameters); layer them one bottleneck at a time — [Introducing advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)
- 2026 STATE: In Claude Code, "MCP tool definitions are deferred by default and loaded on demand via tool search, so only tool names and server instructions consume context until Claude uses a specific tool" — [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works). Agent SDK: read-only tools run concurrently, state-modifying tools sequentially; custom tools default to sequential unless `readOnlyHint` is set — [How the agent loop works](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- 2026 STATE (Fable 5.1): in bash-and-editor harnesses the model "may issue [independent calls] one per turn instead"; fix is a turn-scoped nudge: "First privately list what you need next; then request every item that doesn't depend on another's result in this one response" — [Prompting Claude Fable 5.1](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1)
- 2026 STATE (Opus 5.5): forced tool use (`tool_choice: any/tool`) returns a 400; "To make the model call a tool rather than reply in text, say in the prompt when the tool applies" — [What's new in Claude Opus 5.5](https://platform.claude.com/docs/en/models/opus-5-5/whats-new-opus-5-5)
- Skill-level tool rule: in skills "always use fully qualified tool names... Format: `ServerName:tool_name`" to avoid "tool not found" — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)

### Inferences
- The 2024 ACI appendix and the 2025 tools post have not been superseded; they were *mechanised* — tool search, programmatic calling, and examples are Anthropic implementing its own advice at the platform layer.
- The recurring measurable lever is description text and error text; the recurring measurable metric is tokens per task and tool-error count.

### Gaps
- No 2026 engineering post dedicated to tool design was found; 2026 changes are in docs (tool search default-on, parallel-execution semantics, forced-tool-use removal).

## Key question 3: "How we built our multi-agent research system" (Jun 13, 2025)

### Takeaway
The June 2025 post is Anthropic's most concrete orchestrator-subagent playbook: delegate with an objective, output format, tool guidance and boundaries; scale subagent count and tool-call budgets to query complexity; tokens explain 80% of performance variance and cost ~15× a chat; start evals with ~20 real queries and an LLM judge; and design for stateful resumption and rainbow deployments.

### Cited Findings
- Architecture: orchestrator-worker; lead agent (Claude Opus 4) "analyzes it, develops a strategy, and spawns subagents to explore different aspects simultaneously"; a **CitationAgent** ensures "all claims are properly attributed to their sources" — [Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Numbers: multi-agent Opus 4 lead + Sonnet 4 subagents "outperformed single-agent Claude Opus 4 by 90.2%" on an internal research eval; token usage "explains 80% of the variance" in BrowseComp performance; agents use "about 4× more tokens than chat interactions" and multi-agent systems "about 15× more tokens than chats"; parallelisation "cut research time by up to 90% for complex queries" — [Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Eight prompting principles: (1) "Think like your agents" via simulations; (2) teach delegation — each subagent needs "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries"; (3) scale effort to complexity — "Simple fact-finding requires just 1 agent with 3-10 tool calls, direct comparisons might need 2-4 subagents with 10-15 calls each"; (4) tool design is critical; (5) let agents improve themselves (tool-testing agent, 40% faster completion); (6) "start wide, then narrow"; (7) guide thinking with extended/interleaved thinking as "a controllable scratchpad"; (8) parallel tool calling — [Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Evaluation: "start small" with "about 20 queries representing real usage patterns"; LLM-as-judge rubric on "factual accuracy", "citation accuracy", "completeness", "source quality", "tool efficiency"; human evaluation catches e.g. "SEO-optimized content farms over authoritative... sources" — [Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Production: "When errors occur, we can't just restart from the beginning: restarts are expensive and frustrating for users" → resume from checkpoints; "rainbow deployments" to "avoid disrupting running agents"; limitation — "synchronous execution" where "the lead agent can't steer subagents"; async is future work — [Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- 2026 FOLLOW-ON (superseding the sync limitation for new models): Fable 5 "prefer asynchronous communication between orchestrator and subagents over blocking until each subagent returns. Long-lived subagents that keep their context across subtasks save time and cost through cache reads" — [Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5); Fable 5.1 has a section "Let the lead agent keep working while subagents run" — [Prompting Claude Fable 5.1](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1)
- 2026 FOLLOW-ON (time budgets): for Opus 5.5 multi-agent harnesses, append `elapsed 340s / 1200s` to each message; "Teams given a budget kept answer quality comparable to the single agent's while finishing considerably sooner... a budget mostly keeps more agents working in parallel"; budget is advisory, keep your own timeout — [Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)
- 2026 FOLLOW-ON (multiagent failure modes, Research, Aug 13, 2026): named problems are coordination failures, **low-variance conformity** ("All that differentiates one agent from another is its context, its scaffolding, and the model"; "Eighteen of thirty agents simultaneously created a git branch named 'mvp-game-loop'"), **epistemic brittleness** ("miscalibrated trust" in both directions), and incompatible-goal escalation; coordinated swarms found 266 vulnerabilities vs 21 for independent parallel agents; "coordination doesn't naturally emerge from stronger intelligence nor alignment at the individual level" — [Patterns and problems in multiagent systems](https://www.anthropic.com/research/multiagent-systems)
- 2026 FOLLOW-ON (parallel coding at scale, Feb 5, 2026, Nicholas Carlini): 16 agents in Docker containers sharing a git repo, text-file locks in `current_tasks/`; ~2,000 Claude Code sessions, 2B input / 140M output tokens, ~$20,000, 100,000-line compiler that builds Linux 6.9; lessons: "it's important that the task verifier is nearly perfect"; "log all important information to a file so Claude can find it when needed"; split by "fixing different bugs in different files" to avoid a single-task bottleneck — [Building a C compiler with a team of parallel Claudes](https://www.anthropic.com/engineering/building-c-compiler)

### Inferences
- The June 2025 delegation brief template (objective / output format / tools / boundaries) is still the operative standard; 2026 adds async orchestration, time budgets, and explicit conformity-avoidance (unique names, IDs, lanes) as new requirements.
- Token cost scales with agent count, so Anthropic's own advice is to budget-gate multi-agent use (Barry Zhang's "budget-awareness", Agent SDK `max_budget_usd`, Claude Code subagent caps).

### Gaps
- None material; the post itself is complete. The Research multiagent paper's full methodology was only read via summary extraction.

## Key question 4: "Building agents with the Claude Agent SDK" (Sep 2025) and the gather → act → verify loop

### Takeaway
The Sept 29, 2025 SDK post prescribes the loop "gather context → take action → verify work → repeat", with agentic (grep/tail) search preferred over semantic search, subagents for isolation/parallelism, compaction for length, and three verification modes (rules-based, visual, LLM-judge). In 2026 the same loop is the documented core of Claude Code, and the verification step has hardened into deterministic Stop hooks, `/goal`, and fresh-context reviewer subagents.

### Cited Findings
- EARLIER GUIDANCE (Sep 29, 2025, Thariq Shihipar): loop is "gather context -> take action -> verify work -> repeat" — [Building agents with the Claude Agent SDK](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)
- Gather context: file system as context engineering, using `grep`/`tail` rather than loading whole files; "Semantic search is usually faster than agentic search, but less accurate, more difficult to maintain, and less transparent" — start with agentic search; "Subagents use their own isolated context windows, and only send relevant information back to the orchestrator, rather than their full context"; compaction summarises near the limit — [Building agents with the Claude Agent SDK](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)
- Take action: "Tools are prominent in Claude's context window, making them the primary actions Claude will consider"; bash/scripts for general computer access; "Code is precise, composable, and infinitely reusable, making it an ideal output for agents"; MCP for external integrations — [Building agents with the Claude Agent SDK](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)
- Verify work: "The best form of feedback is providing clearly defined rules for an output, then explaining which rules failed and why" (linting as example); visual feedback via screenshots for UI; LLM-as-judge "is generally not a very robust method, and can have heavy latency tradeoffs" — [Building agents with the Claude Agent SDK](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)
- 2026 STATE: Claude Code docs define the same three phases — "gather context, take action, and verify results" — and name the surrounding layer: "Claude Code is the layer around the model that provides the tools and manages the context the model sees. This surrounding layer is what the term agentic harness refers to" — [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)
- 2026 STATE: the Agent SDK ships "the same tools, agent loop, and context management that power Claude Code"; capabilities table: built-in tools, hooks, subagents, MCP, permissions, sessions, skills/commands/memory, plugins; loop ends when Claude "produces a response with no tool calls"; caps via `max_turns` / `max_budget_usd` ("Setting a budget is a good default for production agents"); budget cap covers subagents (v2.1.217+) — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview); [How the agent loop works](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- 2026 STATE — verification hardened (Claude Code best practices): "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available"; the check is "a test suite, a build exit code, a linter, a script that diffs output against a fixture, or a browser screenshot"; four escalation levels — in one prompt, `/goal`, "As a deterministic gate: a Stop hook runs your check as a script and blocks the turn from ending until it passes", or "By a second opinion: a verification subagent... has a fresh model try to refute the result, so the agent doing the work isn't the one grading it"; "Have Claude show evidence rather than asserting success: the test output, the command it ran and what it returned, or a screenshot" — [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)
- 2026 STATE — `/goal`: "a wrapper around a session-scoped prompt-based Stop hook"; a small fast model (Haiku by default) returns Not-yet-met / Met / Impossible after each turn; "completion is decided by a fresh model rather than the one doing the work"; write conditions with "One measurable end state", "A stated check", "Constraints that matter"; the evaluator "doesn't run commands or read files independently"; loop stops if no tool use for several turns — [Keep Claude working toward a goal](https://code.claude.com/docs/en/goal)
- 2026 STATE — Stop hook cap: "Claude Code overrides a Stop hook after it blocks eight times in a row without progress"; scripts must read `stop_hook_active` and exit early; raise with `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` — [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- 2026 STATE — Agent Skills as the fourth loop primitive: "organized folders of instructions, scripts, and resources that agents can discover and load dynamically"; three-level progressive disclosure (metadata → SKILL.md → bundled files) so bundled context is "effectively unbounded"; "certain operations are better suited for traditional code execution" so skills bundle scripts; author by asking Claude "to capture its successful approaches and common mistakes into reusable context and code"; "We recommend installing skills only from trusted sources" — [Equipping agents for the real world with Agent Skills (Oct 16, 2025)](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)

### Inferences
- Verification is the phase Anthropic has invested in most since 2025: it moved from "give the model feedback" to "make done-ness decided by something other than the working model" (script, fresh evaluator, or reviewer subagent), with evidence shown rather than asserted.
- The SDK post's "LLM-as-judge is not very robust" is refined in 2026: model judges are acceptable when they are *separate*, small, and reading a verifiable transcript (`/goal`), and when code-based graders aren't possible.

### Gaps
- No Anthropic figures on how often Stop-hook gates vs `/goal` vs reviewer subagents catch real defects.

## Key question 5: 2026 guidance (Jan–Sep 2026) — evals, harnesses, auto mode, containment, Claude 5-family prompting

### Takeaway
2026 guidance is about *reliability of unattended agents*: build evals early and grade outcomes not paths (Jan 9); separate generator from evaluator with a sprint contract but remove components as models improve (Mar 24); replace permission prompts with a classifier that refuses scope escalation and exfiltration (Mar 25); contain at the environment layer first (May 25); and, for Claude 5-family models, strip legacy verification/planning scaffolding while adding explicit scope, evidence-grounding, and finish-the-task instructions.

## Key question 6: Principles on simplicity, transparency of planning, verification/self-checking, and context

### Takeaway
Across 2024–2026 Anthropic holds four constant principles — simplest thing first, planning steps visible, verification by something other than the author, and context treated as a finite, degrading resource ("context rot") — while the specific *mechanisms* it recommends have shifted toward deterministic hooks, fresh-context reviewers, and de-scaffolded prompts for Claude 5 models.

### Cited Findings
- Simplicity (2024): "Maintain simplicity in your agent's design" and start with single calls — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents). (2026): "only increase complexity when needed" — [Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Transparency (2024): "explicitly showing the agent's planning steps" — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents). (2025): "throw the entire agent's trajectory into Claude and ask" for diagnosis — [dev.to summary of Barry Zhang talk](https://dev.to/bokuno_log/how-we-build-effective-agents-3-principles-from-anthropics-barry-zhang-gfo). (2026): research prompts should "Update a hypothesis tree or research notes file to persist information and provide transparency" — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Context as finite resource (Sep 29, 2025): "context rot" — "as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases"; system prompts at "the right altitude" ("specific enough to guide behavior effectively, yet flexible enough to provide... strong heuristics"); "just in time" retrieval via lightweight identifiers; long-horizon techniques — compaction (preserve "architectural decisions, unresolved bugs, and implementation details while discarding redundant tool outputs"), structured note-taking (NOTES.md / CLAUDE.md), sub-agents returning "condensed summaries (typically 1,000-2,000 tokens)"; guiding rule: "find the smallest set of high-signal tokens that maximize the likelihood of your desired outcome" — [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- 2026 reaffirmation: "Most best practices are based on one constraint: Claude's context window fills up fast, and performance degrades as it fills"; "The context window is the most important resource to manage"; "After two failed corrections, `/clear` and write a better initial prompt"; the "trust-then-verify gap" — "If you can't verify it, don't ship it" — [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)
- Self-checking limits: "agents tend to respond by confidently praising the work" — [Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps); "A fresh context improves code review since Claude won't be biased toward code it just wrote"; reviewer "sees only the diff and the criteria you give it, not the reasoning that produced the change"; caveat — "A reviewer prompted to find gaps will usually report some, even when the work is sound... Tell the reviewer to flag only gaps that affect correctness or the stated requirements" — [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)
- CLAUDE.md discipline: "For each line, ask: 'Would removing this cause Claude to make mistakes?' If not, cut it. Bloated CLAUDE.md files cause Claude to ignore your actual instructions!"; "If Claude already does something correctly without the instruction, delete it or convert it to a hook"; emphasis on one line only — "If you emphasize many lines, none of them stands out" — [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)
- Skill discipline: "The context window is a public good"; "Default assumption: Claude is already very smart"; "Keep SKILL.md body under 500 lines"; "Keep references one level deep from SKILL.md"; "Set appropriate degrees of freedom" (low freedom + exact scripts for fragile sequences like migrations); "Prefer scripts for deterministic operations"; "Create evaluations BEFORE writing extensive documentation"; avoid time-sensitive info; descriptions in third person with triggers — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
- Subagent discipline: descriptions "take up context, so keep them short"; warning at 15,000 tokens of combined descriptions; defaults — spawn depth 3, 20 concurrent; subagents do not inherit conversation history — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Plugin footprint: "An enabled plugin is part of every session, not only the sessions where you use it"; name+description of every model-invocable skill/agent/command "are in Claude's context on every turn"; official-marketplace plugins show a "Context cost" estimate; "what the plugin runs, it runs as you" — [Plugins overview](https://code.claude.com/docs/en/plugins/overview)

### Inferences
- "Transparency of planning" in 2026 is realised less by the model narrating and more by artifacts: plan files, progress files, notes, evaluator verdicts, workflow scripts you can read and rerun.
- For Claude 5 models, Anthropic's advice to remove "verify your work" prose while keeping deterministic gates means the verification principle is unchanged but its owner changed from prompt to harness.

### Gaps
- Anthropic gives no quantitative CLAUDE.md-length or skill-count thresholds beyond "200 lines", "500 lines", and the 15k-token subagent-description warning.

## Key question 7: Implications for a Claude Code plugin repo (create-cmp)

### Takeaway
Anthropic's guidance maps almost one-to-one onto a repo that holds coding agents to a machine-enforced definition of done: put the definition of done in programs (hooks, scripts, graders) not prose; make evidence the unit of trust; keep skills concise and script-backed; brief subagents with objective/format/tools/boundaries and review in fresh context; cap fan-out; treat every harness component as an ablatable hypothesis per model release; and eval the plugin with `claude plugin eval` against a no-plugin baseline.

### Cited Findings
(Each item pairs an Anthropic rule with the repo design it implies. Sources are the primary pages cited above.)

- **Workflows for the predictable, agent for the ambiguous.** Anthropic: workflows are "predefined code paths"; use agents for tasks "where you can't predict the subtasks" — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents). Implication: the repo's deterministic programs (proof schedule, lane pricing, stage exit, ground-truth counts, defect numbering) are the workflow layer; the agent's freedom lives inside a lane. A rule that can be computed should be a program, not a skill paragraph — consistent with "Put guardrails in hooks... an instruction is a request, not a guarantee" — [Extend Claude Code](https://code.claude.com/docs/en/features-overview).
- **Hooks are the enforcement layer; CLAUDE.md is advisory.** "Hooks are deterministic and guarantee the action happens" — [Best practices](https://code.claude.com/docs/en/best-practices); "A real guardrail needs to be deterministic" — [Steering Claude Code](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more). Implication: definition-of-done gates belong in `PreToolUse` (deny with a `permissionDecisionReason` that is "specific and actionable", per the tools post) and `Stop` hooks; a Stop gate must honour `stop_hook_active` and the 8-consecutive-block cap or raise `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` — [Hooks guide](https://code.claude.com/docs/en/hooks-guide). Hooks cost zero context unless they return output — [Extend Claude Code](https://code.claude.com/docs/en/features-overview).
- **Evidence, not assertion, is the unit of done.** "Have Claude show evidence rather than asserting success" — [Best practices](https://code.claude.com/docs/en/best-practices); "audit each claim against a tool result from this session" — [Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5); "it's important that the task verifier is nearly perfect" — [C compiler](https://www.anthropic.com/engineering/building-c-compiler); "Grade what the agent produced, not the path it took" — [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). Implication: evidence receipts should attest *execution* (timestamps, exit codes, artefact hashes) so a cached or replayed pass cannot be mistaken for a fresh one; receipts should record outcomes, not step sequences.
- **Done-ness decided by something other than the author.** "so the agent doing the work isn't the one grading it" — [Best practices](https://code.claude.com/docs/en/best-practices); "Separate, fresh-context verifier subagents tend to outperform self-critique" — [Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5); evaluator agent + sprint contract — [Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps). Implication: a reviewer subagent should receive the diff and the brief/spec, not the author's report; tell it to "flag only gaps that affect correctness or the stated requirements" and to land findings as failing tests rather than prose — [Best practices](https://code.claude.com/docs/en/best-practices). The "sprint contract" maps to a signed brief that fixes what done means before code is written.
- **Do not tell Claude 5 models to verify; do gate them.** Remove "include a final verification step" / "use a subagent to verify" instructions and "legacy harness scaffolding that adds separate verification steps" for Opus 5 — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5). Implication: audit skills and agent prompts for "double-check"/"re-verify" prose per model; keep the deterministic gates. Also audit for "show your reasoning" instructions, which can trigger `reasoning_extraction` refusals on Fable 5 / Opus 5.5 — [Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5); [Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5).
- **Scope and test-creep controls belong in the brief.** Fable 5.1 block: "Commit tests only where the task asks for them... don't turn scratch checks into additional permanent test files"; Opus 5: "Deliver what was asked, at the scope intended" — [Prompting Claude Fable 5.1](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1); [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5). Implication: executor briefs should carry an explicit scope clause and a "report follow-ups, don't fix them" clause.
- **Unattended runs: a text-only end of turn is a report, not completion.** "Treat a text-only end of turn as a report rather than as proof the task is done... stop after two or three automatic continuations" — [Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5); `/goal` and Stop hooks re-check after every turn; `/goal` skips evaluation while subagents/background shells run — [Keep Claude working toward a goal](https://code.claude.com/docs/en/goal). Implication: an orchestrator that "waits on a review" it never spawned is the documented early-stop failure; the harness should detect open checklist items and resume with a named instruction, bounded to 2–3 continuations.
- **Subagent briefs: objective, output format, tools, boundaries.** — [Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system). Effort scaled to complexity (1 agent/3–10 calls for fact-finding; 2–4 subagents/10–15 calls for comparisons). Implication: agent definitions should fix `tools`, `model`, `effort`, `maxTurns`; briefs should state the output artefact; use `omitClaudeMd` where a subagent should not inherit repo prose — [Subagents](https://code.claude.com/docs/en/sub-agents).
- **Cap fan-out deterministically; prefer async lead.** `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`, `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`, `max_budget_usd` — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5); "Delegate independent subtasks to subagents and keep working while they run" — [Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5); time budgets `elapsed Ns / Ms` — [Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5). Implication: put spawn caps in `.claude/settings.json` env and a budget in orchestrator briefs; multi-agent cost is ~15× chat — [Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system).
- **Avoid low-variance conformity in parallel agents.** 18/30 agents chose the same branch name — [Patterns and problems in multiagent systems](https://www.anthropic.com/research/multiagent-systems); C-compiler run used per-task lock files and file-partitioned bugs — [C compiler](https://www.anthropic.com/engineering/building-c-compiler). Implication: allocate identifiers (defect numbers, branch names, worktrees) from a program, never from each agent's guess; partition work by file/subsystem.
- **Skills: concise, script-backed, evaluation-first, side-effect skills manual-only.** "Keep SKILL.md body under 500 lines"; "Prefer scripts for deterministic operations"; "Create evaluations BEFORE writing extensive documentation"; third-person descriptions with triggers; "Avoid time-sensitive information" — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices); `disable-model-invocation: true` for skills with side effects — [Extend Claude Code](https://code.claude.com/docs/en/features-overview). Implication: release/publish/refresh skills should be user-invocable only; version numbers and counts should come from a script, not skill prose; each skill should have ≥3 eval cases.
- **CLAUDE.md: <200 lines, only what Claude can't infer, convert repeats to hooks.** — [Best practices](https://code.claude.com/docs/en/best-practices); [Extend Claude Code](https://code.claude.com/docs/en/features-overview). Implication: a session map that points to programs rather than restating rules is the recommended shape; a rule stated twice is a candidate for a hook or a script.
- **Context budget: subagents return summaries; compaction is instructed.** Subagents return "1,000-2,000 tokens" — [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents); compaction instructions in CLAUDE.md ("always preserve the full list of modified files and any test commands") — [Best practices](https://code.claude.com/docs/en/best-practices); Fable 5.1 six-item compaction summary spec — [Prompting Claude Fable 5.1](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1). Implication: research/verification goes through subagents; a "Compact Instructions" section should name the artefacts (briefs, receipts, open KDs) that must survive.
- **Long-horizon state lives in files and git.** Feature list JSON with `passes`, `init.sh`, progress file, "It is unacceptable to remove or edit tests", start fresh over compaction — [Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents); [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices). Implication: a slice's state should be reconstructible from the tree (plan file, receipts, git log) so a fresh session can resume; one feature per session.
- **MCP tool design for an inspector server.** Consolidate operations, namespace with a common prefix, `response_format` detailed/concise, pagination/truncation defaults, actionable errors — [Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents); tool-use examples for complex parameters — [Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use); fully qualified `Server:tool` names inside skills — [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices). Implication: measure tokens per inspection task and tool-error counts; let Claude Code rewrite tool descriptions from transcripts.
- **Evals for the plugin itself.** `claude plugin eval`: 3 runs/case, no-plugin baseline arm, free graders (`regex`, `tool_used`, `tool_order`, `file_exists`) plus `llm`/`baseline` judges; pin models in CI — [Test plugins with evals](https://code.claude.com/docs/en/plugin-evals). 20–50 tasks from real failures; capability vs regression suites; pass^k for reliability — [Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). Implication: turn closed known-defects into regression eval cases; gate PRs on the eval exit code; run per-model evals on every system-prompt/skill-text change — [April 23 postmortem](https://www.anthropic.com/engineering/april-23-postmortem).
- **Permissions and containment for a distributed plugin.** Auto mode refuses scope escalation, safety bypass (`--no-verify`-style), agent-inferred parameters — [Auto mode](https://www.anthropic.com/engineering/claude-code-auto-mode); "Treat project-open operations as untrusted input until explicit user authorization"; allowlists are "capability grants" — [How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude); "what the plugin runs, it runs as you" — [Plugins overview](https://code.claude.com/docs/en/plugins/overview). Implication: release acts (merge/publish) need explicit allow rules checked before the run, since the classifier may refuse them even after chat approval; plugin hooks should be minimal, auditable, and never read credentials from the working tree.
- **Re-ablate the harness on every model release.** "Every component in a harness encodes an assumption about what the model can't do on its own" — [Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps); "Skills developed for prior models are often too prescriptive" — [Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5). Implication: keep a per-model checklist (effort default, verification prose, subagent damping, thinking/`reasoning_extraction` constraints) and remove gates that a baseline eval shows the model no longer needs.

### Inferences
- The repo's stated philosophy ("a rule stated twice drifts in one, and a program at the moment of decision beats prose read at session start") is the same conclusion Anthropic reached in its Jun 18, 2026 steering post and its features-overview doc; the remaining Anthropic-recommended additions are plugin evals with a baseline arm, model-specific de-scaffolding, deterministic fan-out caps, and conformity-avoiding identifier allocation.
- Where Anthropic's guidance and a "hold agents to done" harness could conflict is over-gating: Anthropic warns that reviewers "will usually report some [gaps]" and that verification prose causes over-verification on Opus 5 — so the harness should gate on outcomes (receipts, tests) and cap review rounds rather than mandate them.

### Gaps
- Anthropic publishes no guidance specific to Kotlin/Compose Multiplatform or mobile device-tier verification; the closest analogues are browser-automation (Playwright/Puppeteer MCP) evaluators in the harness posts.
- No Anthropic statement was found on hooks-as-gates cost/benefit measured on real repos, nor on how many Stop-hook blocks per turn are healthy.
