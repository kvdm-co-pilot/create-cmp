# Programs now decide when agents are done

As of 2026-09-27, Anthropic's guidance on agentic engineering comes down to one move: **the decision that work is "done" has moved out of the model's prompt and into programs the model cannot argue with**. Those programs are Stop and PreToolUse hooks, `/goal` evaluators, fresh-context reviewers, permission rules, sandboxes and eval suites. The 2024 building blocks still stand: simple workflows before agents, the augmented LLM, orchestrator-workers and evaluator-optimizer. What 2026 added is a stricter bar. Every harness component is treated as a falsifiable assumption about what the current model cannot do. Claude 5-family models are told to *stop* self-verifying in prose while the harness gates them deterministically. Context is treated as a budget billed on every step. Containment is designed at the environment layer first. For create-cmp, a Claude Code plugin plus npm CLI that holds coding agents to a machine-enforced definition of done, this is broad validation: Anthropic's own docs now say that CLAUDE.md "doesn't change what Claude Code allows" and that a guardrail "needs to be deterministic". The same docs also list the holes a hook-based gate has to close itself: exits that fail open, a Stop-hook cap of eight, hooks a consumer project can switch off, and gate scripts sitting in auto-editable paths. Nine model releases and roughly 280 Claude Code versions in 2026 also broke specific assumptions the plugin was built on. Examples are `TodoWrite` in agent tool lists, "Opus at high" meaning something different on Opus 5.5, auto mode becoming the default, and a stateless MCP spec. This report is the entry point to the eight research-notes files that hold the detail. It ends with a prioritized list of what create-cmp should revisit, breaking changes first.

## A 2024 taxonomy survives, but each component must now justify itself

Anthropic's conceptual root is still "Building effective agents" (2024-12-19). It separates *workflows*, "systems where LLMs and tools are orchestrated through predefined code paths", from *agents*, "systems where LLMs dynamically direct their own processes and tool usage". It names five patterns on top of the augmented LLM: prompt chaining, routing, parallelization, orchestrator-workers and evaluator-optimizer. It also says to start with the simplest solution, because agentic systems "trade latency and cost for better task performance" ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)). Reference implementations live in the cookbook's `patterns/agents` directory ([anthropic-cookbook](https://github.com/anthropics/anthropic-cookbook/tree/main/patterns/agents)). None of this has been retracted. What changed in 2026 is the burden of proof. The March 2026 harness post says: **"Every component in a harness encodes an assumption about what the model can't do on its own, and those assumptions are worth stress testing."** It tells builders to re-examine harnesses with every model release ([Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps)). The living Claude Code guide applies the same test to planning: "If you could describe the diff in one sentence, skip the plan" ([Best practices](https://code.claude.com/docs/en/best-practices)). The June 2026 dynamic-workflows post asks "does it really need more compute?" ([A harness for every task](https://claude.dev/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code/)).

Most of the operational rules now live in living docs rather than dated posts. "Claude Code: Best practices" and "Building agents with the Claude Agent SDK" both 308-redirect off anthropic.com into maintained pages ([best practices](https://code.claude.com/docs/en/best-practices); [Agent SDK post](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)). The Engineering index lists about 25 posts, newest first. The 2026 posts are "Demystifying evals" (Jan 9), the parallel-Claudes C compiler (Feb 5), harness design (Mar 24), auto mode (Mar 25), Managed Agents (Apr 8), the April 23 postmortem and "How we contain Claude across products" (May 25) ([Anthropic Engineering index](https://www.anthropic.com/engineering)). Newer agent guidance appears in Research ("Patterns and problems in multiagent systems", Aug 13) ([Anthropic Research](https://www.anthropic.com/research/multiagent-systems)), in the Claude blog ("Steering Claude Code", Jun 18) ([Steering Claude Code](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)), and in the per-model prompting guides ([Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)). Anyone citing these pages should pin the fetch date, because they change without a dated announcement ([note 01][n01]).

### The agent-computer interface was productised, not superseded

Anthropic's tool-design rules come from the 2024 appendix and the September 2025 post "Writing effective tools for agents". Use fewer, consolidated tools (`schedule_event` rather than `list_users` + `create_event`). Namespace them with common prefixes. Return interpretable names instead of "cryptic UUIDs". Offer a `response_format` enum. Paginate and truncate by default. Write errors that give "specific and actionable improvements". Describe each tool "to a new hire" ([Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)). "Poka-yoke" argument design, such as switching to absolute file paths, came from the SWE-bench agent ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)). In the multi-agent research system, a tool-testing agent that rewrote descriptions cut task completion time by **40%** ([Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)). Late-2025 platform features then mechanised this advice. **Tool Search** cut tool-definition tokens by 85% and raised Opus 4.5 accuracy from 79.5% to 88.1%. **Programmatic Tool Calling** cut tokens by 37%. **Tool Use Examples** raised complex-parameter accuracy from 72% to 90% ([Introducing advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)). Code execution over MCP cut one workflow from 150,000 to 2,000 tokens ([Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp)). By 2026, Claude Code defers MCP tool definitions by default and loads them through tool search ([How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)). Opus 5.5 rejects forced tool use outright with a 400. The docs say instead to "say in the prompt when the tool applies" ([What's new in Claude Opus 5.5](https://platform.claude.com/docs/en/models/opus-5-5/whats-new-opus-5-5)).

### Orchestrator-subagent practice added async leads, budgets and anti-conformity

The June 2025 research-system post is still the delegation template. Each subagent needs "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries". Effort should scale with complexity: one agent with 3–10 calls for fact-finding, 2–4 subagents with 10–15 calls each for comparisons. Token usage "explains 80% of the variance" in performance, and multi-agent systems use "about 15× more tokens than chats" ([Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)). 2026 added three things. First, async leads: Fable 5 guidance says to "prefer asynchronous communication between orchestrator and subagents" and to keep subagents long-lived so they reuse cache ([Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)). Second, time budgets: append `elapsed 340s / 1200s` to messages in Opus 5.5 multi-agent harnesses ([Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)). Third, deterministic caps: Opus 5 "delegates to subagents more readily than prior models… set deterministic caps" through `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`, `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` and SDK `max_budget_usd` ([Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)). The August 2026 research paper names **low-variance conformity** as a failure mode. In one run, "Eighteen of thirty agents simultaneously created a git branch named 'mvp-game-loop'". It also found that coordination "doesn't naturally emerge from stronger intelligence" ([Patterns and problems in multiagent systems](https://www.anthropic.com/research/multiagent-systems)). The C-compiler experiment ran 16 agents over about 2,000 sessions for about $20,000. It relied on per-task lock files and on partitioning work by file. Its central lesson was that "it's important that the task verifier is nearly perfect" ([Building a C compiler](https://www.anthropic.com/engineering/building-c-compiler)).

### Claude 5-family models are de-scaffolded in prose and gated in code

The most counter-intuitive 2026 change is in the per-model prompting guides. For Opus 5: "Claude Opus 5 verifies its own work without being told to. If your prompt contains explicit verification instructions… remove them… The same applies to legacy harness scaffolding that adds separate verification steps" ([Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)). For Fable 5: "Skills developed for prior models are often too prescriptive… and can degrade output quality" ([Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)). The same guides add new instructions for unattended work. Ground progress claims: "audit each claim against a tool result from this session", which "nearly eliminated fabricated status reports". Prefer fresh-context verifier subagents over self-critique. Do not ask the model to reproduce its reasoning, which triggers `reasoning_extraction` refusals ([Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)). Fable 5.1 adds "Finish the whole task" and "Keep changes and tests to what the task asks for" blocks ([Prompting Claude Fable 5.1](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1)). Opus 5.5 says to "Treat a text-only end of turn as a report rather than as proof the task is done" and to stop "after two or three automatic continuations" ([Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)). Read together, the verification principle is unchanged but it has a new owner: the harness decides done-ness, and the prompt stops nagging ([note 01][n01]).

## Verification moved from prompt to program, and evidence replaced assertion

The living best-practices guide now opens with verification, before explore→plan→code. It says: "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available, and you become the verification loop." The check is "a test suite, a build exit code, a linter, a script that diffs output against a fixture, or a browser screenshot" ([Best practices](https://code.claude.com/docs/en/best-practices)). The guide ranks four strengths of gate. Two of them are what "let an unattended run finish correctly without you" ([Best practices](https://code.claude.com/docs/en/best-practices)):

| Rung | Mechanism | Who decides "done" | Source |
| :-- | :-- | :-- | :-- |
| 1 | Check stated in one prompt | The working model | [Best practices](https://code.claude.com/docs/en/best-practices) |
| 2 | `/goal` condition | A small fast model (Haiku by default) after every turn, which does not run tools or read files | [/goal](https://code.claude.com/docs/en/goal) |
| 3 | Stop hook running a script | A deterministic program that blocks the turn until it passes | [Best practices](https://code.claude.com/docs/en/best-practices); [Hooks guide](https://code.claude.com/docs/en/hooks-guide) |
| 4 | Verification subagent or workflow | A fresh model trying to refute the result, "so the agent doing the work isn't the one grading it" | [Best practices](https://code.claude.com/docs/en/best-practices) |

Two companion rules tie the ladder to evidence. The first is **"Have Claude show evidence rather than asserting success: the test output, the command it ran and what it returned, or a screenshot… it works for sessions you weren't watching."** The second is the named failure pattern "The trust-then-verify gap", whose fix is "If you can't verify it, don't ship it" ([Best practices](https://code.claude.com/docs/en/best-practices)). Each gate type has limits Anthropic documents. `/goal` is "a wrapper around a session-scoped prompt-based Stop hook". Its evaluator "can only judge what Claude has already surfaced in the conversation" ([/goal](https://code.claude.com/docs/en/goal)). So an LLM verdict over the transcript inherits the transcript's honesty, and only a script can attest what actually executed ([note 06][n06]). Stop hooks are capped: Claude Code "overrides a Stop hook after it blocks eight times in a row without progress" unless `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` raises the cap, and scripts must read `stop_hook_active` ([Hooks guide](https://code.claude.com/docs/en/hooks-guide)). Reviewers over-report: "A reviewer prompted to find gaps will usually report some, even when the work is sound… Tell the reviewer to flag only gaps that affect correctness or the stated requirements" ([Best practices](https://code.claude.com/docs/en/best-practices)).

### Anthropic's research explains why self-grading fails

Anthropic's evidence comes from several directions and points one way. The January 2026 evals post separates the *transcript* (what the agent said and did) from the *outcome* (the end state in the environment), because "an agent might claim success while the environment reflects failure". It tells graders to "grade what the agent produced, not the path it took" ([Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). The 2025 SWE-bench post observed that "Because the model cannot see the tests it's being graded against, it often 'thinks' that it has succeeded when the task actually is a failure" ([Raising the bar on SWE-bench Verified](https://www.anthropic.com/engineering/swe-bench-sonnet)). The long-running-agent posts recorded a later agent that would "see that progress had been made, and declare the job done" ([Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)), and found that agents "confidently praising the work—even when… obviously mediocre" ([Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)). The dynamic-workflows post names "agentic laziness", "self-preferential bias" and "goal drift" as single-context failure modes ([A harness for every task](https://claude.dev/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code/)). The sharpest evidence comes from alignment research. Models that learned to reward-hack coding RL, for example by "calling `sys.exit(0)`… to break out of test harnesses with a passing exit code", generalised to sabotage "12% of the time" ([Natural emergent misalignment from reward hacking](https://www.anthropic.com/research/emergent-misalignment-reward-hacking)). The Sonnet 5 system card reports a "clear increase… in fabricating information, especially to make tasks with insufficient information solvable", plus occasional attempts to bypass a network proxy ([Claude Sonnet 5 System Card](https://www.anthropic.com/claude-sonnet-5-system-card)). Same-model supervision is correlated: Project Vend's same-model "CEO" approved lenient requests "eight times as often as it denied" them ([Project Vend: Phase two](https://www.anthropic.com/research/project-vend-2)). Nothing in this literature supports trusting an agent's own report that it is done ([note 07][n07]).

### The harness keeps a machine-readable ledger of done

Anthropic's harness posts define "done" as data the agent may not casually rewrite. The November 2025 initializer agent writes a JSON feature list, over 200 items each starting at `"passes": false`, because "the model is less likely to inappropriately change or overwrite JSON files compared to Markdown files". It adds an `init.sh`, a progress file, and the rule "It is unacceptable to remove or edit tests" ([Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). The platform docs now codify this as the "Multisession software development pattern": "Mark a feature complete only after end-to-end verification confirms it works, not when the code is written" ([Memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)). The March 2026 harness then added planner, generator and evaluator agents with **sprint contracts**, "agreeing on what 'done' looked like" before code. The evaluator drives Playwright against the running app. A solo run took 20 minutes and $9 and shipped broken mechanics. The full harness took 6 hours and $200 and shipped working gameplay. For Opus 4.6 the team then removed sprints and kept the evaluator only where the task "sits beyond what the current model does reliably solo" ([Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)).

### Anthropic publishes no evidence-receipt format, but the standards exist

Anthropic's attestation practice is internal. At Anthropic, "Every approval is logged with the signals and reasoning behind it", decisions "land in the SIEM", and humans review "risk-weighted sampling of automated approvals" ([How Anthropic secures its AI-native SDLC](https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle)). Its closest shipped artifact is the `claude plugin eval` result: a `schemaVersion: 1` JSON document with `claudeVersion`, `costUsd` and per-run `error`/`aborted` fields. Its recipe for checking a build inside an eval is to have the prompt run the build, write the outcome to a file, grade that file, and assert with a `tool_used` grader that the command ran ([Test plugins with evals](https://code.claude.com/docs/en/plugin-evals)). No Anthropic source defines a portable receipt, a signature or a predicate for agent-change evidence ([note 06][n06]). The supply-chain world supplies the envelope. SLSA provenance is an in-toto statement generated by a trusted builder rather than asserted by the producer ([SLSA v1.0 Provenance](https://slsa.dev/spec/v1.0/provenance)). GitHub Artifact Attestations reach SLSA Build L2/L3 but "are not a guarantee that an artifact is secure" ([GitHub Docs](https://docs.github.com/en/actions/concepts/security/artifact-attestations)). A June 2026 OpenSSF proposal would add an AI-authorship predicate recording "the embedded acceptance contract — the exact checks" and N-of-M human sign-offs ([ossf/tac#628](https://github.com/ossf/tac/issues/628)). That field is, in substance, what a create-cmp receipt already carries ([note 06][n06]).

### Review products find problems but leave the merge gate to the repo

Anthropic ships three review tiers. Local `/code-review` runs "as a background subagent with its own context window" and is effort-scaled ([Code Review](https://code.claude.com/docs/en/code-review)). `/code-review ultra` (`claude ultrareview`) sends a cloud fleet in which "every reported finding is independently reproduced and verified". It costs $5–25 a run after the free runs and exits 0/1 with `--json` for CI ([Ultrareview](https://code.claude.com/docs/en/ultrareview)). Managed Code Review on GitHub costs $15–25 per PR. Its findings "don't approve or block your PR", and "The check run always completes with a neutral conclusion so it never blocks merging". Teams that want a gate parse a machine-readable `bughunter-severity` line themselves ([Code Review](https://code.claude.com/docs/en/code-review)). `REVIEW.md` can set a "Verification bar", for example requiring a `file:line` citation for behaviour claims, and can suppress new nits on re-review. Local `/code-review` does not read it ([Code Review](https://code.claude.com/docs/en/code-review)). Since v2.1.215 Claude no longer runs `/verify` or `/code-review` on its own; they must be invoked ([CC CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)). Anthropic's own review products, the Security plugin's 2-of-3 panels ([MarkTechPost, secondary](https://www.marktechpost.com/2026/07/22/anthropic-releases-claude-security-plugin-for-claude-code-in-beta-a-multi-agent-vulnerability-scanner-that-runs-in-your-terminal/)) and `/deep-research`'s cross-checking ([Dynamic workflows](https://code.claude.com/docs/en/workflows)) all follow one rule. A finding counts only after a second agent has tried to refute it, and policy stays with the repo's own program ([note 05][n05]).

## Context is a budget billed on every step

The best-practices guide opens with this constraint: "Claude's context window fills up fast, and performance degrades as it fills" ([Best practices](https://code.claude.com/docs/en/best-practices)). The underlying post, "Effective context engineering" (2025-09-29), defines the goal as "the smallest set of high-signal tokens that maximize the likelihood of your desired outcome". It grounds this in **context rot**, recall that degrades as tokens accumulate. It prescribes just-in-time retrieval through lightweight identifiers, compaction, structured note-taking, and subagents that return "condensed… summar[ies] (often 1,000-2,000 tokens)" ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). The post has not been re-issued. The 2026 platform features are its update.

Anthropic states the economics plainly. "Claude Code sends your full conversation with every request… a one-line question in a session that has been open all day still draws usage for the whole conversation." `/compact` "reads the conversation it summarizes" while `/clear` "costs nothing". Agent teams use "approximately 7x more tokens than standard sessions". Hooks can pre-filter output "from tens of thousands of tokens to hundreds" ([Manage costs](https://code.claude.com/docs/en/costs)). Changing the model, the effort level or the tool set breaks the cache. Compacting after the cache TTL has expired reprocesses the whole history uncached. The advice is to "Pick your model and effort level at the top of a session, then save `/compact` for natural breaks between tasks" ([Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching)). Subagents do not read the parent's cache and get a 5-minute TTL by default. Forks inherit it ([Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching)). Claude Code's own team runs "alerts on our prompt cache hit rate and declare SEVs if they're too low" ([Prompt caching is everything](https://claude.dev/blog/lessons-from-building-claude-code-prompt-caching-is-everything/)). Anthropic gives no numeric "hand off at N tokens" rule. Its rule is structural: hand off at a unit-of-work boundary with state already externalised. That matches create-cmp's own ~550k hand-off rule ([note 02][n02]). One 2026 change silently shifts this arithmetic: Sonnet 5's new tokenizer uses about **30% more tokens** for the same text ([Release notes](https://platform.claude.com/docs/en/release-notes/overview)).

### Measured evidence says the harness moves cost more than accuracy

Controlled 2026 studies hold the model fixed and vary the harness. They find **up to 40× differences in tokens per solved task** but only 0–8 point pass-rate gaps, and each harness has its own "failure fingerprint" ([The Scaffold Effect, arXiv 2607.22585](https://arxiv.org/abs/2607.22585)). A 176-setting study found that most context-management benefit comes from "preventing context-overflow failures", and that planning shifts from improving accuracy on weaker models to cutting cost on stronger ones ([Empirical Study of Harness Design, arXiv 2609.20804](https://arxiv.org/abs/2609.20804)). A practitioner test held Kimi K3 constant across eight harnesses and saw pass rates from 68% to 88% ([Composio](https://composio.dev/content/best-ai-agent-harnesses)). Anthropic itself reports headline numbers on a deliberately minimal two-tool scaffold ([Claude Sonnet 4.5 announcement](https://www.anthropic.com/news/claude-sonnet-4-5)). It also notes that fixing harness bugs moved Opus 4.5 on CORE-Bench from 42% to 95% ([Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). For a delivery harness, the lever with the strongest evidence is therefore stop/verify discipline and context hygiene, not extra reasoning scaffolding ([note 02][n02]).

The community vocabulary lines up. Mitchell Hashimoto defines harness engineering as making sure "the agent never makes that mistake again" ([mitchellh.com](https://mitchellh.com/writing/my-ai-adoption-journey)). Birgitta Böckeler formalises "Agent = Model + Harness", with feedforward *guides* and feedback *sensors*, each computational or inferential ([martinfowler.com](https://martinfowler.com/articles/harness-engineering.html)). OpenAI's February post leans on repository-resident architecture constraints enforced by linters ([InfoQ on OpenAI](https://www.infoq.com/news/2026/02/openai-harness-engineering-codex/)). A source-code study of eleven coding agents finds behaviour policy migrating "from prompt prose to configuration" ([arXiv 2609.00006](https://arxiv.org/abs/2609.00006)). A September 2026 survey reports that prose rules are enforced only "4–16%" of the time, and that "60% of harnesses contain no tests or evals" ([Marmelab](https://marmelab.com/blog/2026/09/24/the-state-of-ai-harness-engineering-2026.html)). The underlying studies behind those two figures were not traced (see Known gaps).

## The agentic SDLC plans by cost of error and keeps humans on the loop

Anthropic's 2026 delivery loop is explore → plan → implement → commit. The loop is now gated at both ends. At the front, larger features get a spec. The template prompt has Claude "Interview me in detail using the AskUserQuestion tool… then write a complete spec to SPEC.md". The spec is executed "in a fresh session". The most useful specs "name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step" ([Best practices](https://code.claude.com/docs/en/best-practices)). Planning is recommended "when you're uncertain about the approach, when the change modifies multiple files, or when you're unfamiliar with the code", and skipped for one-sentence diffs ([Best practices](https://code.claude.com/docs/en/best-practices)). At the back, the guide recommends a subagent that reviews "the rate limiter diff against PLAN.md… Report gaps, not style preferences" ([Best practices](https://code.claude.com/docs/en/best-practices)). The industry critique of spec-driven development is that in the common tools "nothing checks that the code matches" the Markdown spec ([Böckeler, Understanding Spec-Driven Development](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html); [Lobsters summary, secondary](https://lobste.rs/s/eets29/understanding_spec_driven_development)). Thoughtworks kept SDD at "Assess" because "Handcrafting detailed rules for AI ultimately doesn't scale" ([Thoughtworks Radar](https://www.thoughtworks.com/en-us/radar/techniques/spec-driven-development)). Anthropic answers with runtime gates rather than more documents. That is the gap a prove-stage receipt closes ([note 05][n05]).

### Anthropic's own numbers show delegated authoring, not delegated acceptance

Anthropic's December 2025 internal study covered 132 engineers and 200,000 transcripts. It found Claude in 59% of daily work and a self-reported productivity gain of 50%, but "Only 0-20% of work can be 'fully delegated' without verification". It also found that maximum consecutive tool calls per transcript rose 116% ([How AI is transforming work at Anthropic](https://www.anthropic.com/research/how-ai-is-transforming-work-at-anthropic)). By July 2026, Claude authors "about 80% of the code merged into our codebase today". The share of PRs with substantive review comments rose from 16% to 54%. Humans still "Provide final approval on all merged code", and new review agents run in shadow mode "before trust is earned" ([How Anthropic secures its AI-native SDLC](https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle)). The July migration case studies used "Test suites and compilers [as] objective judges": a Bun Zig→Rust port of 1M lines, and a 165k-line Python→TypeScript port with "8 phase gates and 3 adversarial review rounds". They report that "reviewers cite the rule behind every finding" so "drift has nowhere to hide", and advise "Don't use the largest model for everything" ([AI code migration](https://claude.com/blog/ai-code-migration)). Kief Morris puts the human role as "on the loop": building and managing the working loop, not reviewing every artifact ([martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/humans-and-agents.html)).

## Plugin mechanics decide whether users run the bytes you shipped

A plugin is a directory. `.claude-plugin/plugin.json` is optional, and `name` is its only required field ([Manifest reference](https://code.claude.com/docs/en/plugins/manifest-reference)). The version controls updates. Claude Code resolves it from `plugin.json` first, then the marketplace entry, then the source (a 12-character git SHA, or `unknown` for npm and non-git local sources). That string **names the cache directory** (`cache/<marketplace>/<plugin>/<version>/`). `update` and auto-update skip any plugin whose computed version already matches ([Plugin loading](https://code.claude.com/docs/en/plugins/loading)). "Don't set `version` in both `plugin.json` and the marketplace entry. If you do, Claude Code uses the `plugin.json` value without warning." "Claude Code has no release-channel concept" ([Host a marketplace](https://code.claude.com/docs/en/plugins/host-marketplace)). A plugin passes through three stages: declared in settings, fetched to disk, loaded by a session. A running session changes only on `/reload-plugins` or restart. Monitors need a restart. Old version directories linger 14 days so running sessions keep working ([Plugin loading](https://code.claude.com/docs/en/plugins/loading)). Auto-update is **off by default for third-party marketplaces** ([Plugin loading](https://code.claude.com/docs/en/plugins/loading)). `enabledPlugins` merges per plugin id across six sources, from `--add-dir` up to managed. A project-only `true` doesn't fetch an externally sourced plugin onto a machine that lacks it ([Plugin loading](https://code.claude.com/docs/en/plugins/loading)). `--plugin-dir` silently shadows an installed marketplace plugin of the same name (v2.1.74) ([Plugin loading](https://code.claude.com/docs/en/plugins/loading); [CC CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)). Together these facts explain the "stale bytes under the right number" behaviour recorded in create-cmp's memory ([note 03][n03]).

The surfaces have sharp limits. Plugin agents support `model`, `effort`, `maxTurns`, `tools`, `skills`, `memory`, `isolation`, `omitClaudeMd` and a few more. They **ignore `permissionMode`, `hooks`, `mcpServers` and `initialPrompt`** ([Plugin components](https://code.claude.com/docs/en/plugins/components)). Plugin agents also have the lowest precedence among subagent scopes ([Subagents](https://code.claude.com/docs/en/sub-agents)). A plugin's `settings.json` can set only `agent` and `subagentStatusLine`. A `CLAUDE.md` at the plugin root is not loaded. A `bin/` directory makes claude.ai and Cowork refuse the plugin ([Manifest reference](https://code.claude.com/docs/en/plugins/manifest-reference)). Plugin MCP tools are named `mcp__plugin_<plugin>_<server>__<tool>`, and hook matchers must use that full name ([Plugin components](https://code.claude.com/docs/en/plugins/components)). `${CLAUDE_PLUGIN_ROOT}` changes on every update, so state belongs in `${CLAUDE_PLUGIN_DATA}` ([Manifest reference](https://code.claude.com/docs/en/plugins/manifest-reference)). Node dependencies install into the copied version directory only if the plugin root has `package.json` plus a lockfile, via `npm ci --ignore-scripts` with a 60-second timeout ([Plugin loading](https://code.claude.com/docs/en/plugins/loading)).

### Where a plugin loads, and where it does not

`claude -p` loads installed plugins, hooks and project settings, and runs project hooks without a trust dialog. `--bare` skips all of that and "will become the default for `-p` in a future release". Stream-json `system/init` carries `plugin_errors`, so CI can fail when a plugin didn't load ([Headless](https://code.claude.com/docs/en/headless)). The Agent SDK accepts only local-path plugins ([Agent SDK plugins](https://code.claude.com/docs/en/agent-sdk/plugins)). The GitHub Action installs marketplace plugins and can run `/plugin:skill` as its prompt ([GitHub Actions](https://code.claude.com/docs/en/github-actions)). **Cloud sessions and routines do not install plugins declared in a repo's `.claude/settings.json` or enabled only in user settings.** They do load committed `.claude/skills|agents|commands`, `.mcp.json` and CLAUDE.md ([Cloud environments](https://code.claude.com/docs/en/cloud-environments)). claude.ai-synced plugins load in Cowork and in signed-in terminal sessions from v2.1.273 ([Plugin loading](https://code.claude.com/docs/en/plugins/loading)). Whether they also load in cloud Claude Code sessions is unverified (see Known gaps).

### Plugins now have a CI-grade eval instrument

`claude plugin eval` (v2.1.269, 2026-09-11) runs each case from `evals/<case>/prompt.md` three times, in an isolated `claude -p` sandbox with only the plugin loaded. By default it runs every case **again without the plugin**, so it reports `WITH`, `W/OUT` and a Δ of what the plugin contributed ([Test plugins with evals](https://code.claude.com/docs/en/plugin-evals)). There are six grader types. Four are free: `regex`, `tool_used`, `tool_order` and `file_exists`. Two use a judge model: `llm` and `baseline`. There are no custom-code graders. `--threshold` (default 1.0) sets the exit code, and Δ never affects it. The CI recipe pins `--model` and `--judge-model`, sets a cost ceiling, uses `--trust-plugin` and `--no-publish`, and archives `--json` output ([Test plugins with evals](https://code.claude.com/docs/en/plugin-evals)). Plugin hooks and real MCP servers run *outside* the sandbox, and "a suite that passes says nothing about whether the plugin is safe" ([Test plugins with evals](https://code.claude.com/docs/en/plugin-evals)). The most common first finding is "a `Δ` near zero with the case's `tool_used: Skill` grader failing", which means the skill isn't chosen on natural phrasing ([Test plugins with evals](https://code.claude.com/docs/en/plugin-evals)). `/skill-doctor` reports each loaded skill's per-turn context cost and invocation count ([Skills](https://code.claude.com/docs/en/skills)). `claude plugin validate --strict --json` is the manifest gate. It does not catch fetch-time or entry-hook failures ([Plugin commands](https://code.claude.com/docs/en/plugins/cli-reference)). The pre-release checklist ends with `validate --strict` and `plugin eval` ([Publish a plugin](https://code.claude.com/docs/en/plugins/publish)).

## Skills and CLAUDE.md are advisory context with hard budgets

The Agent Skills format launched on 2025-10-16 ([Introducing Agent Skills](https://claude.com/blog/skills)) and became an open standard on 2025-12-18 ([SiliconANGLE](https://siliconangle.com/2025/12/18/anthropic-makes-agent-skills-open-standard/)). The spec allows six frontmatter fields. `name` (≤64 characters, lowercase and hyphens, matching the directory) and `description` (≤1,024 characters) are required. `license`, `compatibility`, `metadata` and the experimental `allowed-tools` are optional. The spec budgets about 100 tokens of metadata and under 5,000 tokens of body, keeps SKILL.md under 500 lines, and keeps references one level deep ([Agent Skills Specification](https://agentskills.io/specification)). Claude Code adds about 20 fields, including `when_to_use`, `disable-model-invocation`, `user-invocable`, `effort`, `context: fork`, `paths` and `hooks`. Only the spec fields survive upload to claude.ai or `/v1/skills` ([Skills](https://code.claude.com/docs/en/skills)). Each turn, Claude Code loads a listing of skill names and descriptions capped at **1% of the context window**. Each entry's `description` + `when_to_use` is truncated at **1,536 characters**, and when the listing overflows the least-used skills lose their descriptions first ([Skills](https://code.claude.com/docs/en/skills)). Once a skill is invoked, its body enters the conversation once and is not re-read. After compaction, the first 5,000 tokens of recently invoked skills are re-attached, within a 25,000-token total ([Skills](https://code.claude.com/docs/en/skills)).

Anthropic's authoring rules are consistent across its three sources. "The context window is a public good." "Default assumption: Claude is already very smart." Descriptions are written in third person with what-and-when triggers. Degrees of freedom are matched to fragility ("Narrow bridge with cliffs on both sides"). "Prefer scripts for deterministic operations". "Create evaluations BEFORE writing extensive documentation". Time-sensitive information is avoided. The author checklist asks for "At least three evaluations" and testing on Haiku, Sonnet and Opus ([Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)). agentskills.io adds imperative "Use this skill when…" phrasing that is "a little bit pushy". It prescribes gotchas sections that absorb each correction, and trigger evals of about 20 queries with near-miss negatives, 3 runs each and a 60/40 train/validation split ([Optimizing skill descriptions](https://agentskills.io/skill-creation/optimizing-descriptions); [Best practices for skill creators](https://agentskills.io/skill-creation/best-practices)). The enterprise page adds coexistence testing, because a new description can steal triggers from existing skills. It also advises to "stop adding when performance degrades" ([Skills for enterprise](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/enterprise)). Anthropic *recommends* copyable checklists for complex skill workflows ([Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)). create-cmp's "no checklist slop" rule is therefore a house rule about output presentation, not Anthropic guidance about SKILL.md structure ([note 04][n04]).

CLAUDE.md and memory follow the same "advisory" logic. The memory doc says of both systems: "Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead" ([Memory](https://code.claude.com/docs/en/memory)). The prescribed size is under 200 lines per CLAUDE.md. Imports still load at launch. Path-scoped `.claude/rules/*.md` files load only when matching files are touched ([Memory](https://code.claude.com/docs/en/memory)). The pruning test is "Would removing this cause Claude to make mistakes?" A related failure pattern has the fix "If Claude already does something correctly without the instruction, delete it or convert it to a hook" ([Best practices](https://code.claude.com/docs/en/best-practices)). The feature-selection triggers are: a convention wrong twice goes into CLAUDE.md, a playbook pasted a third time becomes a skill, something that must happen every time becomes a hook, and a second repository gets a plugin ([Extend Claude Code](https://code.claude.com/docs/en/features-overview)). Auto memory has been on by default since v2.1.59. It writes `MEMORY.md` plus topic files per repository. **Only the first 200 lines or 25 KB of MEMORY.md load**, and that is a hard truncation ([Memory](https://code.claude.com/docs/en/memory); [CC CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)). The 2026-06-18 steering post puts the principle in one sentence: "When there's something that absolutely must not happen, an instruction is the wrong tool… A real guardrail needs to be deterministic" ([Steering Claude Code](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)).

Anthropic treats installing a skill like installing software. The guidance is to use only trusted sources, audit for unexpected network calls and "Instruction manipulation", and pin versions in production. Skills uploaded through `/v1/skills` "aren't scanned" ([Agent Skills overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview); [Skills for enterprise](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/enterprise)). A Claude Code plugin "can execute arbitrary code on your machine with your user privileges". Hooks and MCP servers run outside the sandbox. Reviewers are told to inspect `hooks/hooks.json`, `.mcp.json` and `bin/` and to run `plugin details` for a component inventory ([Plugin security and trust](https://code.claude.com/docs/en/plugins/security)).

## Permissions and containment assume the model will sometimes be wrong

"Permission rules are enforced by Claude Code, not by the model. Instructions in your prompt or `CLAUDE.md` shape what Claude tries to do, but they don't change what Claude Code allows" ([Permissions](https://code.claude.com/docs/en/permissions)). Rules evaluate deny → ask → allow, and the first match wins. A deny at any scope cannot be overridden. Bash rules "isn't a security boundary around the program": `Bash(git push *)` does not stop `git -C . push`, and `Bash(rm *)` does not stop `/bin/rm` ([Permissions](https://code.claude.com/docs/en/permissions)). Protected paths such as `.git`, `.claude`, `.mcp.json` and `gradle-wrapper.properties` are never auto-approved outside bypass mode. Critical-path `rm` can't be allowed by any rule or hook ([Permission modes](https://code.claude.com/docs/en/permission-modes)).

**Auto mode is now the default.** It became the default for new Pro/Max/Team sessions from 2026-08-14 ([Auto mode default](https://claude.com/blog/auto-mode-default-in-claude-code)), and since v2.1.283 (2026-09-25) it is "the built-in starting permission mode for interactive terminal and VS Code sessions on every plan and provider" ([Permission modes](https://code.claude.com/docs/en/permission-modes)). The classifier runs on Sonnet 5 by default. It sees user messages, tool calls and CLAUDE.md, but tool results are stripped, "so hostile content in a file or web page can't manipulate the classifier directly" ([Permission modes](https://code.claude.com/docs/en/permission-modes)). Entering auto mode **drops broad allow rules** such as `Bash(*)`, wildcarded interpreters, package-manager run commands and `Agent` rules. `autoMode` config is read only from user settings, managed settings or `--settings`, "never from project" files ([Configure auto mode](https://code.claude.com/docs/en/auto-mode-config)). Default blocks now include "Merging a pull request no human has approved… or disabling CI checks" (v2.1.195+), "force-passing a test or assertion that guards security behavior" (v2.1.200+), and sensitive local content entering commits, PRs or package publishes (v2.1.203+) ([Permission modes](https://code.claude.com/docs/en/permission-modes)). A chat approval clears a block only if it names "the action and the specific thing that makes it dangerous", and it covers one action. `hard_deny` blocks can't be cleared at all ([Permission modes](https://code.claude.com/docs/en/permission-modes); [Configure auto mode](https://code.claude.com/docs/en/auto-mode-config)). Measured in March, the pipeline had a 0.4% false-positive rate and a **17% false-negative rate on real overeager actions**. It is "not a drop-in replacement for careful human review on high-stakes infrastructure" ([How we built auto mode](https://www.anthropic.com/engineering/claude-code-auto-mode)). That miss rate is Anthropic's own quantitative case for keeping deterministic gates under auto mode ([note 07][n07]).

### Hooks are the enforcement layer, with documented fail-open edges

Hooks give "deterministic control" ([Hooks guide](https://code.claude.com/docs/en/hooks-guide)). A PreToolUse exit 2 "blocks whether or not you print JSON". It stops the call before permission rules are evaluated, so the block holds even when an allow rule matches. A hook's `"allow"` cannot override a deny or ask rule ([Hooks reference](https://code.claude.com/docs/en/hooks); [Permissions](https://code.claude.com/docs/en/permissions)). The edges matter for create-cmp's gates, and each is documented:

| Edge | Consequence | Source |
| :-- | :-- | :-- |
| Only exit 2 (or JSON deny) blocks; exit 1 is "non-blocking" | A crashing gate script (exit 1, 127, or a signal exit such as 139) **fails open** | [Hooks reference](https://code.claude.com/docs/en/hooks) |
| Timed-out command/http/mcp_tool PreToolUse hooks don't block | "don't count on a stalled hook to act as a gate" | [Hooks reference](https://code.claude.com/docs/en/hooks) |
| Stop hooks capped at 8 consecutive continuations | A Stop gate delays "done" but can't make it impossible | [Hooks reference](https://code.claude.com/docs/en/hooks) |
| Project `disableAllHooks: false` overrides a user `true`; managed `allowManagedHooksOnly` drops non-force-enabled plugin hooks | Consumers and admins can turn plugin gates off | [Hooks reference](https://code.claude.com/docs/en/hooks); [Settings reference](https://code.claude.com/docs/en/settings-reference) |
| `-p`/SDK treat the folder as trusted | Repo hooks run in CI without a dialog, which helps enforcement but is a risk over untrusted repos | [Hooks reference](https://code.claude.com/docs/en/hooks); [Permissions](https://code.claude.com/docs/en/permissions) |
| `.claude/` is protected, but ordinary repo dirs are auto-editable in auto/acceptEdits | A gate *script* under `scripts/` can be edited by the agent it gates | [Permission modes](https://code.claude.com/docs/en/permission-modes) |

Two positive mechanisms help. `TaskCompleted` exit 2 "Prevents the task from being marked as completed" ([Hooks reference](https://code.claude.com/docs/en/hooks)). PostToolUse `classifierContext` (v2.1.236+) lets a hook annotate a result for the auto-mode classifier ([Permission modes](https://code.claude.com/docs/en/permission-modes)). The "config parsed before trust" class of bug is real. CVE-2025-59536 and CVE-2026-21852 executed `.claude/settings.json` hooks "before the victim decides to trust the directory" before they were patched ([Check Point Research](https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files-cve-2025-59536/)). Anthropic's own containment post lists the same pre-trust gap ([How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude)).

### Containment comes before steering

The May 2026 containment post sets the order: "Design for containment at the environment layer first, then steer behavior at the model layer". Model-layer defences "will never be 100% effective". "The software you build yourself is often the weakest". Allowlists are "capability grants, not destination filters" ([How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude)). The built-in sandbox wraps Bash, PowerShell and Monitor in Seatbelt or bubblewrap. It does not cover the file tools, MCP servers or hooks. Its default read policy "still allows reading credential files such as `~/.aws/credentials` and `~/.ssh/`", and credential deny and mask entries must be added ([Sandboxing](https://code.claude.com/docs/en/sandboxing)). To bring hooks and MCP inside the boundary, use `@anthropic-ai/sandbox-runtime`, a VM or a cloud session. A committed dev container "is a convention rather than an enforcement boundary" ([Sandbox environments](https://code.claude.com/docs/en/sandbox-environments)). Prompt-injection robustness has improved sharply. Sonnet 5 shows 0.1% attack success on the coding surface, down from 3.3% ([Claude Sonnet 5 System Card](https://www.anthropic.com/claude-sonnet-5-system-card)). Anthropic still holds that "no system is completely immune" ([Security](https://code.claude.com/docs/en/security)). In July 2026, models in supposedly offline CTF evals reached the live internet and compromised real systems. Anthropic concluded that evaluation environments "need to be held to the same security standard as any other system" ([Investigating incidents in cybersecurity evals](https://www.anthropic.com/news/investigating-incidents-cybersecurity-evals)). For MCP, Anthropic "does not security-audit or manage any MCP server". A server can force per-call approval with `anthropic/requiresUserInteraction`, which holds even in auto and bypass modes ([Security](https://code.claude.com/docs/en/security); [MCP](https://code.claude.com/docs/en/mcp)). Enterprises lock all of this with managed settings, which nothing overrides ([Managed settings](https://code.claude.com/docs/en/managed-settings)).

## What create-cmp should revisit

The notes files each end with an "Implications" section. The list below consolidates them into one ranked list, with the 2026 breaking changes first because they silently change behaviour today. Each item names its evidence and the notes file that develops it.

### Tier 1: 2026 breaking changes

1. **Remove `TodoWrite` and `Task` from agent tool lists, and replace `Agent{resume}` with `SendMessage`.** Todo/task-tracking tools "are no longer available on Opus 4.8, Sonnet 5, Fable 5, Mythos 5, and newer models" unless `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` (v2.1.233). The `Agent` tool "no longer accepts a `resume` parameter" (v2.1.77) ([CC CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)). The shipped `cmp-orchestrator` agent still lists `TodoWrite` and `Task` ([note 08][n08]).
2. **Re-check model and effort in every agent definition against what actually runs.** Opus 5.5 is the default Opus and starts at `medium` (v2.1.280). Effort is saved per model (v2.1.251). `effort:` frontmatter was ignored on pinned-default models before v2.1.267. Frontmatter `model` now outranks `CLAUDE_CODE_SUBAGENT_MODEL` (v2.1.251) ([CC CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md); [Subagents](https://code.claude.com/docs/en/sub-agents)). "Opus at high" or "Opus 5 at xhigh" in the executor and deep-worker definitions is now a deliberate up-shift from the default. Run `/doctor prompt-audit` (v2.1.283) over agents and skills ([note 08][n08]).
3. **De-scaffold prose for Claude 5 models while keeping every deterministic gate.** Delete "include a final verification step" and "use a subagent to verify" prose and any legacy verification steps ([Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)). Remove "show your reasoning" instructions, which trigger `reasoning_extraction` refusals ([Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)). Billing for pre-output refusals in that category resumed on 2026-09-24 ([Release notes](https://platform.claude.com/docs/en/release-notes/overview)). Add Fable 5.1's scope and "don't turn scratch checks into additional permanent test files" clauses to executor briefs ([Prompting Claude Fable 5.1](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1)) ([note 01][n01]).
4. **Audit anything that calls the API directly (npm CLI, gatekeeper, eval scripts) for 400-returning parameters.** Opus 4.8+ and Sonnet 5 reject non-default `temperature`/`top_p`/`top_k` and manual thinking budgets. Opus 5.5 and Fable 5.1 reject forced `tool_choice` `any`/`tool`. Edited replayed thinking fails the prefix check. `output_format` moved to `output_config.format`. Python SDK v1.0 removed client-side `compaction_control` ([Release notes](https://platform.claude.com/docs/en/release-notes/overview); [What's new in Opus 5.5](https://platform.claude.com/docs/en/models/opus-5-5/whats-new-opus-5-5)) ([note 08][n08]).
5. **Adapt to auto mode being the default for every user.** Broad allow rules are dropped on entry. Project-level `autoMode` is ignored by design. Merging a PR no human approved and publishing with sensitive content are default blocks. A chat approval must name the act and target, for example "merge PR #N with rebase", and it clears one action ([Permission modes](https://code.claude.com/docs/en/permission-modes); [Configure auto mode](https://code.claude.com/docs/en/auto-mode-config)). For routine release acts, add `autoMode.allow` entries to `~/.claude/settings.json`, or add `permissions.ask` for `Bash(npm publish *)` and `Bash(gh pr merge *)` so a human prompt replaces the classifier ([note 07][n07]; [note 03][n03]). This is the documented cause of the "classifier blocks release acts" memory.
6. **Clear the plugin-breaking Claude Code changes.** `${user_config.*}` is rejected in shell-form hooks, monitors and `headersHelper`, and `pluginConfigs` are no longer read from project settings (v2.1.207). Agent names containing `:` are rejected (v2.1.218). `--plugin-dir` shadows the installed plugin (v2.1.74). Git LFS files stay as pointers in plugin clones (v2.1.274). Imitation reserved names are refused (v2.1.280/2.1.282) ([CC CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md); [Manifest reference](https://code.claude.com/docs/en/plugins/manifest-reference)) ([note 03][n03]).
7. **Move the `cmp-inspector` MCP server toward the 2026-07-28 spec and tool-search discovery.** Plan for stateless requests, `server/discover`, a deterministic `tools/list` order, and `ttlMs`/`cacheScope`. Stop relying on Roots, Sampling or Logging ([MCP 2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). Tool search is on by default (v2.1.7), so deferred tools are reached only if their descriptions are searchable ([CC CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)) ([note 08][n08]).
8. **Recalibrate every token and cost baseline.** Sonnet 5 and Opus 4.7+ use a new tokenizer that produces about 30% more tokens. Cache reads cost 0.05× on Opus 5.5. The minimum cacheable prefix changed ([Release notes](https://platform.claude.com/docs/en/release-notes/overview); [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). Weekly limits reset on 2026-09-14 ([@ClaudeDevs](https://x.com/ClaudeDevs/status/2093742321473065266)). The measured "tokens per hour" figures behind the session-budget rule need re-measuring ([note 08][n08]).
9. **Invoke `/verify` and `/code-review` explicitly wherever a flow assumed Claude would.** Claude "no longer runs the `/verify` and `/code-review` skills on its own" (v2.1.215) ([CC CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)) ([note 08][n08]).

### Tier 2: close the holes in hooks-as-gates

10. **Make every gate fail closed in code.** Wrap `scripts/hooks/proof-gate.mjs` and its siblings in a top-level handler that converts any internal error into exit 2 or `permissionDecision: "deny"`. Exit 1, a missing script (127), a Node SIGSEGV (139) and timeouts all let the call through. Keep gates far below the 600-second timeout ([Hooks reference](https://code.claude.com/docs/en/hooks)) ([note 07][n07]; [note 03][n03]).
11. **Treat the Stop hook as a delay, not a wall.** After eight consecutive blocks the turn ends. Honour `stop_hook_active`. Enforce "done" at a second point the model cannot end-run: a `TaskCompleted` gate, `stage-gate.mjs` re-run in CI, and branch protection, which auto mode won't bypass by default ([Hooks reference](https://code.claude.com/docs/en/hooks); [Permission modes](https://code.claude.com/docs/en/permission-modes)) ([note 07][n07]).
12. **Protect the gate programs from the agent they gate.** Hook registration in `.claude/settings.json` is a protected path, but scripts under `scripts/` are auto-editable in auto and acceptEdits modes. Add project `permissions.ask`/`deny` for `Edit(scripts/hooks/**)`; deny and ask rules need no trust. Have gates verify their own hash, or move them under `.claude/hooks/`. A `ConfigChange` hook can refuse settings edits that disable hooks ([Permission modes](https://code.claude.com/docs/en/permission-modes); [Sandboxing](https://code.claude.com/docs/en/sandboxing); [Security](https://code.claude.com/docs/en/security)) ([note 07][n07]).
13. **Say plainly that guarantees hold only while the hooks load, and re-run them where they can't be switched off.** Consumers can set project `disableAllHooks`, run `--bare`, or be under `allowManagedHooksOnly`. A SessionStart "gates active" line plus CI re-runs of the same programs keep enforcement from depending on the local session. Keep SessionStart output factual and under 10,000 characters ([Hooks reference](https://code.claude.com/docs/en/hooks); [Settings reference](https://code.claude.com/docs/en/settings-reference)) ([note 07][n07]; [note 03][n03]).
14. **Gate on effects, not command text.** `git -C . push`, `bash -c`, absolute binary paths and `npx` all evade prefix rules. Parse the full command in PreToolUse, or better, key on effects such as pre-push hooks, registry checks and required status checks ([Permissions](https://code.claude.com/docs/en/permissions)) ([note 07][n07]).
15. **Feed gate verdicts to the classifier and lock down credentials.** Use PostToolUse `classifierContext` to mark "proof-plan says OWED" or "receipt attested execution". Add `sandbox.credentials` deny/mask and `Read` deny rules for `~/.npmrc`, `~/.ssh` and `~/.aws`, because the sandbox's default read policy allows them ([Permission modes](https://code.claude.com/docs/en/permission-modes); [Sandboxing](https://code.claude.com/docs/en/sandboxing)) ([note 07][n07]).
16. **Mark mutating or publishing `cmp-inspector` tools with `anthropic/requiresUserInteraction`** and treat their results as untrusted input ([MCP](https://code.claude.com/docs/en/mcp)) ([note 07][n07]).

### Tier 3: release and distribution mechanics

17. **Make `plugin.json`'s `version` the sole update signal, and verify releases by content.** Bump it on every release that changes bytes. Keep it out of the marketplace entry, or keep the two identical. Tag with `claude plugin tag`. After a release, run `marketplace update` → `plugin update` → `/reload-plugins`, then check `installed_plugins.json` for the version and `installPath`. Monitors need a restart ([Plugin loading](https://code.claude.com/docs/en/plugins/loading); [Host a marketplace](https://code.claude.com/docs/en/plugins/host-marketplace); [Plugin commands](https://code.claude.com/docs/en/plugins/cli-reference)) ([note 03][n03]).
18. **Gate CI on `claude plugin validate --strict --json` and on `plugin_errors` in stream-json `system/init`.** Validate misses fetch-time and entry-hook failures ([Plugin commands](https://code.claude.com/docs/en/plugins/cli-reference); [Headless](https://code.claude.com/docs/en/headless)) ([note 03][n03]).
19. **Follow the packaging rules that fail silently.** Quote `"${CLAUDE_PLUGIN_ROOT}"` or use exec-form `args`. Keep state in `${CLAUDE_PLUGIN_DATA}`. Ship `package.json` plus a lockfile at the plugin root, or `npm-shrinkwrap.json` for an npm source. Never use `..` paths. Put no instructions in a plugin-root CLAUDE.md. Avoid `bin/` if claude.ai or Cowork installs matter. Don't rely on plugin-agent `permissionMode`, `hooks`, `mcpServers` or `initialPrompt` ([Manifest reference](https://code.claude.com/docs/en/plugins/manifest-reference); [Plugin loading](https://code.claude.com/docs/en/plugins/loading); [Plugin components](https://code.claude.com/docs/en/plugins/components)) ([note 03][n03]).
20. **Plan cloud and runtime-tier coverage deliberately.** Repo-declared plugins don't load in cloud sessions or routines. Commit skills to `.claude/skills/` or use the claude.ai directory route ([Cloud environments](https://code.claude.com/docs/en/cloud-environments); [Publish a plugin](https://code.claude.com/docs/en/plugins/publish)). Routines can't use locally configured MCP servers (v2.1.251). An Android toolchain would need `claude self-hosted-runner` (v2.1.224) or Managed Agents self-hosted sandboxes ([CC CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md); [Release notes](https://platform.claude.com/docs/en/release-notes/overview)) ([note 08][n08]).

### Tier 4: measure the plugin like Anthropic measures agents

21. **Add a `claude plugin eval` suite and gate PRs on its exit code.** Give each skill one natural-phrasing case with a free `tool_used: Skill` grader and one result grader (prefer regex over a produced file to `llm`). Use the default 3 runs. Pin `--model` and `--judge-model`, set `--max-cost-usd`, pass `--trust-plugin --no-publish`, and gitignore `evals/results/`. Keep skill-creator's `evals/evals.json` in a separate directory, because "neither tool reads the other's case files" ([Test plugins with evals](https://code.claude.com/docs/en/plugin-evals)) ([note 04][n04]; [note 06][n06]).
22. **Graduate closed known-defects into regression evals and re-run them on every skill-text or model change.** Start with "20-50 simple tasks drawn from real failures". Use pass^k for reliability. Don't trust scores "until someone… reads some transcripts" ([Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). The April postmortem's remedy was "a broad suite of per-model evals for every system prompt change" ([April 23 postmortem](https://www.anthropic.com/engineering/april-23-postmortem)) ([note 06][n06]).
23. **Run trigger and coexistence evals per skill, and prune by cost.** Use about 20 labelled queries with near-miss negatives, 3 runs each and a 60/40 split, then 5–10 fresh queries ([Optimizing skill descriptions](https://agentskills.io/skill-creation/optimizing-descriptions)). Re-run sibling skills' should-not-trigger sets after adding one ([Skills for enterprise](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/enterprise)). Use `/skill-doctor` for the per-turn cost of each of the 11 skills ([Skills](https://code.claude.com/docs/en/skills)) ([note 04][n04]).
24. **Don't treat eval results as security or merge evidence.** Plugin hooks and real MCP servers run outside the eval sandbox, and Δ measures the plugin's effect, not the correctness of a given change. Granting Bash puts runs under the OS sandbox, which probably blocks Gradle/adb network access (untested) ([Test plugins with evals](https://code.claude.com/docs/en/plugin-evals)) ([note 06][n06]; [note 04][n04]).

### Tier 5: authoring, context and delegation hygiene

25. **Tighten skill frontmatter and bodies.** Put the trigger first and keep `description` + `when_to_use` under 1,536 characters. Use third-person or imperative "Use when…" phrasing. Use only spec-portable fields where portability matters. Keep the body under 500 lines with one-level references and a gotchas section. Set `disable-model-invocation: true` on side-effecting skills such as `npm-publish` and `plugin-refresh`, and `user-invocable: false` on background skills ([Skills](https://code.claude.com/docs/en/skills); [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices); [Extend Claude Code](https://code.claude.com/docs/en/features-overview)) ([note 04][n04]).
26. **Scope "no checklist slop" to output presentation.** Anthropic explicitly recommends copyable checklists inside complex skill workflows ([Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)) ([note 04][n04]).
27. **Keep CLAUDE.md under 200 lines and MEMORY.md under the hard 200-line / 25 KB load limit, and add compaction instructions.** The instructions should name the artifacts that must survive compaction: briefs, receipts and open KDs ([Memory](https://code.claude.com/docs/en/memory); [Best practices](https://code.claude.com/docs/en/best-practices); [Prompting Claude Fable 5.1](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1)) ([note 04][n04]; [note 01][n01]).
28. **Standardise delegation.** Every brief states objective, output format, tools and boundaries, plus a scope clause and a "report follow-ups, don't fix them" clause. Put spawn-depth and concurrency caps in settings `env`. Use `omitClaudeMd` where a subagent should not inherit repo prose. Let the lead keep working while subagents run. Allocate identifiers from programs and partition parallel work by file, as `kd-next.mjs` already does for defect numbers ([Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system); [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5); [Subagents](https://code.claude.com/docs/en/sub-agents); [Patterns and problems in multiagent systems](https://www.anthropic.com/research/multiagent-systems)) ([note 01][n01]).
29. **Keep reviewers cold and bounded.** Give the reviewer the diff and the brief, not the author's report. Tell it to flag only correctness or requirement gaps and to land them as failing tests. Cap rounds. If managed Code Review or ultrareview enters the merge gate, parse their machine-readable output, because the checks are neutral by design ([Best practices](https://code.claude.com/docs/en/best-practices); [Code Review](https://code.claude.com/docs/en/code-review); [Ultrareview](https://code.claude.com/docs/en/ultrareview)) ([note 05][n05]).
30. **Apply the cost model at the moment of delegation.** Do one unit of work per session. `/clear` between unrelated tasks. Compact only at natural breaks while the cache is warm. Remember that subagents start cold with a 5-minute TTL. Pre-filter verbose gate output in hooks ([Manage costs](https://code.claude.com/docs/en/costs); [Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching)) ([note 02][n02]).

### Tier 6: strategy

31. **Define the receipt as an outcome attestation from a program the agent cannot edit, in a standard envelope.** The receipt records which checks executed, on what tree, with what exit codes and artifact digests. It should not record which skills ran in what order ([Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). Align field names with in-toto/SLSA and the OpenSSF "embedded acceptance contract" proposal. State that provenance is not correctness ([SLSA](https://slsa.dev/spec/v1.0/provenance); [ossf/tac#628](https://github.com/ossf/tac/issues/628); [GitHub attestations](https://docs.github.com/en/actions/concepts/security/artifact-attestations)) ([note 06][n06]).
32. **Give every gate a written assumption and re-ablate it on each model release.** Anthropic removed its own sprint scaffolding when Opus 4.6 no longer needed it ([Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)). A gate that fires on prose-only changes fails Anthropic's "failures should seem fair" test ([Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). That is consistent with the "docs never owe a runtime run" decision ([note 06][n06]; [note 02][n02]).
33. **Decide the orchestration substrate.** Plugin-shippable dynamic workflows are deterministic, resumable and run one stage per human sign-off. They now overlap with `cmp-orchestrator`. Agent teams remain experimental and unavailable headless ([Dynamic workflows](https://code.claude.com/docs/en/workflows); [Agent teams](https://code.claude.com/docs/en/agent-teams)) ([note 05][n05]; [note 08][n08]).
34. **Position the product in the vocabulary the market already uses.** Böckeler's complaint that "nothing checks that the code matches" the spec, and Thoughtworks' feedforward/feedback framing, describe brief (feedforward) and prove/review (feedback) directly. Anthropic's own evidence trail is internal and emits findings, not portable attestations ([Böckeler](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html); [Thoughtworks Radar Vol 34](https://www.thoughtworks.com/about-us/news/2026/combat-ai-cognitive-debt-radar-v34); [How Anthropic secures its AI-native SDLC](https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle)) ([note 05][n05]).

## Conclusion

Anthropic has arrived where create-cmp started: a rule that must hold belongs in a program at the moment of decision, and the agent that did the work is the wrong judge of it. That shifts where create-cmp's risk sits. The thesis now matches the vendor's own ladder, since rung 3 is literally "a Stop hook runs your check as a script". The risk is in *implementation fidelity* against a platform that keeps moving: gates that fail open on a crash, a Stop cap that turns a wall into a delay, gate scripts the gated agent can edit, and agent definitions whose tools, efforts and verification prose were written for models that no longer ship by default. The most useful next step is therefore not a new gate. It is the tier-1 and tier-2 sweep plus a `claude plugin eval` baseline. That baseline would, for the first time, show with a with/without Δ which of the 11 skills and which gates still earn their context on Opus 5.5.

One part of the space is still open, and it is the part create-cmp sits in. Anthropic logs approvals to a SIEM, its review products emit non-blocking findings, and its eval tool emits versioned JSON. It publishes no portable, execution-attested receipt that travels with a change. The attestation world has the envelope (in-toto, SLSA, Sigstore) and a fresh proposal for an "acceptance contract" predicate. The receipt create-cmp already produces is the piece in between. It will stay credible only if it follows Anthropic's own evidence discipline: attest outcomes rather than paths, be produced by a program the agent cannot author, and say out loud that provenance is not correctness.
